# دليل التشغيل المحلي (Local Runbook)

> التنسيق: Docker Compose (D‑26). البنية التحتية فقط من القائمة المعتمدة: PostgreSQL · PgBouncer · Redis · MinIO · Qdrant · Vault · Nginx + App/Workers (FastAPI/Uvicorn).
>
> ✅ **مكتمل — 7.3.** كانت الأوامر أدناه «مرجعية» حتّى المرحلة 7؛ صارت الآن **مقيسةً على مكدّسٍ حيّ**. كلّ ما يحمل ⚠️ في هذه الوثيقة عُثر عليه بالتشغيل لا بالمراجعة.

## 1) المتطلبات المسبقة
- Docker + Docker Compose v2
- Python 3.12+ و `uv` (أو `pip`) لتشغيل الأدوات محلياً خارج الحاوية
- `make` (اختياري، لاختصار الأوامر)

> لا شيء آخر. `openssl` و`vault` و`mc` كلّها تعمل **داخل صورٍ مثبّتة الأوسمة** عبر خدماتٍ لمرّةٍ واحدة، فلا يُشترط وجودها على المضيف.

## 3) الإقلاع

### 3.0 الإقلاع السريع
```bash
cp .env.example .env      # املأ القيم غير السرّية؛ أسرار التطبيق تُبذَر في Vault
docker compose up -d      # الترتيب كلّه مُرمَّزٌ في depends_on
```
هذا وحده يكفي محليّاً: يرفع البيانات، ثمّ الخدمات الأربع لمرّةٍ واحدة (تهيئة Vault وMinIO والشهادة والهجرات)، ثمّ التطبيق والمُرحّل والحافّة.

**حزام الاختبارات الحيّ** يستعمل المكدّس نفسه، لكنّه يطلب ملف التجاوز صراحةً كي ينشر التضمين ويُحضِر سكربت قاعدة الاختبار:

```bash
docker compose -f docker-compose.yml -f docker-compose.test.yml up -d
docker compose -f docker-compose.yml -f docker-compose.test.yml \
  exec -T postgres sh /opt/aizzak/testdb/20-test-database.sh
set -a; . ./.env.test; set +a
REQUIRE_LIVE=1 pytest -rs
```

`docker-compose.test.yml` لا يُقرأ تلقائياً، ولا ينشئ قاعدة الاختبار عند الرفع: السطر الثاني فعل تزويدٍ صريح قابل لإعادة التشغيل. و`.env.test` ملف محلّي متجاهَل يحمل الاعتمادات الفعلية؛ لا تستبدله بقيم `.env.test.example` النائبة.

> ⚠️ **بين السطرين — قِس أطوال الأسرار الثمانية، ولا تكتفِ بحارس `:?`.** كلمات مرور Postgres السبع (‏المستخدم الخارق + أصحاب الأدوار الستّة) و`MINIO_ROOT_PASSWORD` معها محميّةٌ كلّها في `docker-compose.yml` بـ`${VAR:?...}`، والحارس يرفض **غير المضبوط والفارغ** فقط: قيمة `change-me-*` المنسوخة من `.env.example` تمرّ صامتة. و`10-roles.sh` يعمل **مرّةً واحدةً** عند تهيئة الحجم الأوّل ⇒ ما يُقرأ هنا يُولد به الدور و**يبقى**: لا إصلاحَ بعدها إلّا `ALTER ROLE` يدويّةً بصلاحيّة المستخدم الخارق (‏§3.3‑ب). ‏`MINIO_ROOT_PASSWORD` أهون قليلاً — MinIO يقرأ جذره من البيئة في **كلّ** إقلاع، فتغييرُه لاحقاً يسري بإعادة إنشاء الحاوية — لكنّه يبقى اعتماداً منشوراً حتّى تفعل، و`deploy/vault/bootstrap.sh` يبذر القيمة نفسها في `secret/minio` فيلزم أن يُعاد تشغيله معها. هذا ليس افتراضاً: `TRANSIT_ROTATOR_PASSWORD` وُجد placeholder في `.env` الحيّة يوم §3.97 (الفقرة (هـ))، ولا حارسَ آليّ يكشفه لأنّ `.env` غير متعقَّبةٍ في git. لا تطبع القيمة — الطول وحده:

```bash
for v in POSTGRES_SUPERUSER_PASSWORD AIZZAK_OWNER_PASSWORD APP_RW_PASSWORD \
         OUTBOX_RELAY_PASSWORD RETENTION_SWEEPER_PASSWORD METRICS_READER_PASSWORD \
         TRANSIT_ROTATOR_PASSWORD MINIO_ROOT_PASSWORD; do
  l=$(grep "^${v}=" .env); l=${l#*=}; printf "%-28s len=%s\n" "$v" "${#l}"   # 32، ولا يبدأ بـchange-me
done
grep "^MINIO_ROOT_USER=" .env   # معرّفٌ لا سرّ: لا قاعدةَ طولٍ عليه، لكن لا يبقى change-me-* أيضاً
```

> ⚠️ **`docker compose up -d` لا يعيد بناء صورةٍ قائمة** (ن‑4، `release-blockers-plan.md §5‑ب`؛ اكتُشفت §3.83). Compose يبني صورةً **غائبة** فقط — صورةٌ موجودةٌ بنفس الاسم/الوسم تستمرّ تُقلَع من محتواها **القديم** مهما تغيّر `src/`/`Dockerfile` تحتها، بلا أيّ فشل فحص صحّةٍ يكشف ذلك (‏`docker compose ps` تقول `healthy` على الصورة البائتة تماماً كما على الطازجة — نفس عائلة عرَض §3.88's «صحّةٌ خضراء على سلوكٍ خاطئ»). **بعد أيّ تعديلٍ على `src/`/`Dockerfile`**: إمّا `docker compose build <service>` ثمّ `up -d <service>`، أو مباشرةً `docker compose up -d --build`.

```bash
# 4) فحص الصحّة (تفصيلها في §5)
curl -s  http://localhost/health          # liveness
curl -sk https://localhost/health/ready   # readiness عبر TLS
```

### 3.1 مصادقة Vault: Token محلّي مقابل AppRole (`D‑22`)

**أيّ المتغيّرات مضبوطة هو المفتاح**، لأنّ `create_vault_client` **يفضّل التوكن متى وُجد**:

| الوضع | `VAULT_TOKEN` | `VAULT_ROLE_ID` | `VAULT_SECRET_ID` |
|---|---|---|---|
| Token (تجاوزٌ يدويّ — نادر) | توكنٌ جذرٌ حقيقيّ (§3.4) | — | — |
| **AppRole (الوضع العاديّ، محلّيّاً وفي كلّ بيئةٍ أخرى)** | **فارغ** | من Vault | يُحقن خارج الملفّ |

> ⚠️ `VAULT_TOKEN=` الفارغ **ليس قيمةً ناقصة، بل هو المُبدِّل**. تركُ توكنٍ مضبوطاً بجانب زوج AppRole يعني أنّ الزوج لا يُستعمل إطلاقاً — والنشر يبدو ناجحاً.

`vault-bootstrap` يُنشئ الدور والسياسة في **كلّ** بيئة (بما فيها المحلّية)، لسببين: هذه الخطوة نفسها هي ما يعيد إنشاء الدور على أوّل إقلاعٍ أو بعد فقدان حجم `vault-data` (§3.4 — الحالة الوحيدة الآن التي تفقد فيها Vault شيئاً)؛ ومسارُ مصادقةٍ لا يُهيَّأ إلّا في الإنتاج هو مسارٌ **يُجرَّب أوّل مرّةٍ في الإنتاج**.

```bash
# 1) اقرأ role_id (غير سرّي — 05 §2). محلّياً مثبَّتٌ في .env فلا ينجرف.
docker compose exec vault vault read -field=role_id auth/approle/role/app/role-id

# 2) اسكك secret_id (سرّيّ). ⚠️ `exec` لا `run`: مخرجات exec لا يلتقطها
#    سائق سجلّات json-file، ومخرجات خدمةٍ يلتقطها ويحتفظ بها.
docker compose exec vault vault write -f -field=secret_id auth/approle/role/app/secret-id

# 3) أقلع بـAppRole وحدها — لا توكن إطلاقاً
VAULT_TOKEN= VAULT_SECRET_ID='<الملتقَط أعلاه>' docker compose up -d app
```

**السياسة**: `deploy/vault/app-policy.hcl` — قراءة `secret/data/*` و`update` على `transit/{encrypt,decrypt,rewrap}/tenant-secrets` **فقط**. مشتقّةٌ من مواضع النداء في `vault_secrets.py` لا من الكتالوج. الدور يُنشأ بـ`token_no_default_policy=true`، وإلّا أضاف Vault سياسة `default` المدمجة فوقها وبطل وصف الملفّ.

- **`transit/rewrap` مُمنوحةٌ منذ P1‑9 (خطوة 12، §4.5 أدناه)** — أُضيفت مع أوّل مستدعٍ لها (`app.ops.rotate_transit`)، لا قبله (سابقة §3.75‑ب: «صلاحيةٌ لا يمارسها أحدٌ صلاحيةٌ مجّانيّة»). **لا تزال `transit/keys/tenant-secrets/rotate` (إدارة المفتاح، لا استخدامه) غير ممنوحةٍ عمداً**.
- ⚠️ **`client.is_authenticated()` يعيد `False` لتوكنٍ سليمٍ تماماً** تحت هذه السياسة: إنّه ينادي `auth/token/lookup-self` وهو ممنوع. لا تُضِفه «فحصَ سلامة» في `create_vault_client` — يمنعه `deploy/smoke/approle_smoke.py` صراحةً.

**⚠️ عمر التوكن — مقيسٌ لا مُفترَض.** `token_ttl=1h` أعلاه حقيقيّ: قِيس على دورٍ مؤقّتٍ عمره ثماني ثوانٍ أنّ **KV وTransit كليهما** يبدآن بالفشل لحظة انتهاء التوكن. وVault على **مسار التشغيل** لا الإقلاع وحده (كلّ عمليّة `credentials`/`integrations` تمرّ بـTransit)، فالعَرَض تطبيقٌ يخدم الطلبات ساعةً ثمّ يعجز عن لمس أيّ سرّ مستأجِر — و`/health/ready` **أخضر طوال الوقت** لأنّه لا يسبر أيّ تبعيّة عمداً. العلاج مُنفَّذ: `VaultSecrets` يُعيد المصادقة **مرّةً واحدة** عند رفضٍ بـ403/401 ثمّ يعيد المحاولة (`create_approle_relogin`). محاولةٌ واحدة لا حلقة: الرفض الثاني يعني اعتماداً خاطئاً لا منتهياً، والحلقة تحوّل خطأ إعدادٍ إلى عاصفة تسجيل دخولٍ على Vault.

> ⚠️ **`secret_id` ينقضي بعد 24 ساعة (ن‑10، `p1-hardening-plan.md §5‑ب`)، ولا شيء يُجدِّده اليوم — والفشل صامت.** `deploy/vault/bootstrap.sh` يضبط `secret_id_ttl=24h` (إلى جانب `token_ttl=1h`/`token_max_ttl=4h` أعلاه). محاولة `relogin` المذكورة أعلاه تستعمل نفس `VAULT_SECRET_ID` القديم — فإن كان **هو نفسه** منتهياً (لا التوكن وحده)، تفشل بـ`400 invalid role or secret ID`، وهو **بالضبط** نفس الخطأ الذي يعطيه زوجٌ خاطئٌ عمداً، فلا تُشتبَه بالنظرة الأولى بأنّها انقضاءً لا اعتماداً خاطئاً. **العرَض**: بعد أكثر من 24 ساعةً من الإقلاع، كلّ ما يعتمد على Vault (فكّ تعمية اعتمادات `credentials`/`integrations`، أسرار MinIO) يبدأ بالفشل بينما `docker compose ps` يستمرّ يقول `healthy` — لأنّ فحص الصحّة لا يلمس Vault إطلاقاً (نفس السبب الذي يُبقي `/health/ready` أخضر أثناء انقضاء التوكن أعلاه). **سكّ `secret_id` جديد**: كرّر §3.1's الخطوة 2 أعلاه (`docker compose exec vault vault write -f -field=secret_id auth/approle/role/app/secret-id`) ثمّ أعِد تشغيل `app` بـ`VAULT_SECRET_ID` الجديد.
>
> **القرار بين ثلاثة بدائل:** **(أ)** تجديدٌ دوريٌّ آليّ لـ`secret_id` (سايدكار أو `vault agent`) قبل الانقضاء · **(ب)** رفع `secret_id_ttl` مع توثيق المقايضة (نافذةٌ أطول لسرقة `secret_id` صالح) · **(ج)** قبول السلوك كما هو، مع **فحص صحّةٍ يكشفه** بدل إخفائه. ✅ **حُسم 2026‑07‑30 بـ(ب) للمكدّس المحلّيّ**: `secret_id_ttl=720h` في `deploy/vault/bootstrap.sh` مع تعليلٍ ملاصق. النشر الحقيقيّ يبقى على (أ) — التوقيت القصير مع تجديدٍ فعليّ.

> 🔴 **الفخّ الذي يُبطل العلاج نفسه — انكشف في عُطلٍ حقيقيٍّ 2026‑07‑30 (§3.94)، واقرأه قبل أن تُصلح شيئاً.** حين ينقضي `secret_id` ثمّ **تُعاد تشغيل الحاويات** (إعادة تشغيل Docker/WSL تكفي)، لا يفشل التطبيق مرّةً واحدة — بل يدخل **حلقة انهيارٍ** يحاول فيها `gunicorn` بعث عاملَيه مراراً، وكلّ محاولةٍ تسجيل دخولٍ فاشلة. فتتدخّل **ميزة قفل المستخدم في Vault** (`user lockout`) وتقفل الاسم المستعار للدور:
>
> ```
> vault: [ERROR] core: login attempts exceeded, user is locked out: request_path=auth/approle/login
> ```
>
> ومنذ تلك اللحظة يصير **`secret_id` جديدٌ صحيحٌ تماماً مرفوضاً أيضاً** — والرفض يأتي بشكلٍ مضلّلٍ ثالث: **`403 permission denied` بقائمة أخطاءٍ فارغة**، لا `400 invalid role or secret ID`. فالمشغّل الذي يطبّق العلاج الصحيح (سكّ سرٍّ جديد) يراه «لا يعمل» فيشكّ في سياسةٍ أو دورٍ أو صلاحيّة، والسبب أنّ محاولاته نفسها هي ما يُبقي القفل قائماً.
>
> **الترتيب الصحيح للإصلاح — أوقف الحلقة أوّلاً، وإلّا أعدتَ إشعال القفل بيدك:**
>
> ```bash
> docker compose stop app
> ```
>
> ثمّ افكّ القفل بتوكن الجذر (‏`/vault/init/init.json` داخل حاوية `vault`): `vault write -f sys/locked-users/<mount_accessor>/unlock/<role_id>` — و`mount_accessor` من `vault auth list`، و`role_id` هو `aizzak-local-app` هنا. تحقّق من القفل قبله وبعده بـ`vault read sys/locked-users`. ثمّ اسكك `secret_id` جديداً وأعد إنشاء `app`.
>
> ⚠️ **`docker compose start app` ليس كافياً ولا آمناً هنا**: إنّه يُقلع الحاويات **القائمة ببيئتها المخبوزة وقت إنشائها**، فلا يرى `.env` المحدَّث إطلاقاً — وهو يجرّ معه `vault-bootstrap` و`migrate` فيعملان باعتمادٍ بائت (‏`vault-bootstrap` يُعيد بذر `secret/db` بالسرّ القديم، فيمحو تدويراً جديداً بلا إنذار). المطلوب `docker compose up -d --force-recreate --no-deps <service>` لكلّ خدمةٍ تحمل اعتماداً مُدوَّراً.

**🆕 الكشف صار موجوداً: مقياسٌ ثالثٌ على `/metrics` وإنذارٌ ثالث (ن‑10، النصف المتمّم).** رفعُ `secret_id_ttl` إلى `720h` يؤخّر العطب ولا يكشفه؛ فأُضيف **`aizzak_vault_authenticated`** — قيمةٌ `1` حين تستطيع هذه العمليّة إجراء نداء Vault مُصرَّحٍ به الآن، و`0` في كلّ ما عدا ذلك (سرٌّ منقضٍ أو مُبطَل يفشل تسجيل دخوله، Vault مختوم، اتّصالٌ مرفوض، مهلةٌ منتهية — لا تمييز بينها من هنا). ويقابله إنذار **`AizzakVaultAuthFailing`** (`< 1` لمدّة `5m`، **`severity: critical`** خلافاً لتحذيرَي Outbox/DLQ: هذا فقدُ قدرةٍ لا تراكمُ عمل — مسار `credentials`/`integrations` **يفشل فعلاً** لحظة قراءة الصفر، وإعادة التشغيل التالية لن تُقلع أصلاً).

- **السبر نفسه**: قراءة KV لمسارٍ **لا يكتب فيه أحد** (`secret/data/_probe/vault-health`). منحة `read` على `secret/data/*` قائمةٌ أصلاً، فمسارٌ فارغٌ يعيد 404 من Vault نفسها ⇒ `NotFoundError` ⇒ **صحّة** (بلوغ الـ404 يعني أنّ الطلب صُودق عليه وسُمح به). **لا تغييرَ في Vault مطلوبٌ إطلاقاً**: لا منحةَ سياسةٍ جديدة، ولا تعديلَ دور، ولا إعادةَ تشغيل.
- **لماذا ليس `is_authenticated()`**: يعيد `False` لتوكنٍ سليمٍ تماماً تحت هذه السياسة (`auth/token/lookup-self` ممنوع — أعلاه). مقياسٌ مبنيٌّ عليه يقرأ `0` إلى الأبد.
- **لماذا ليس عمر `secret_id` المتبقّي** — وهو الرقم الأنفع لأنّه يُنذر **قبل** الموت: يحتاج `auth/approle/role/app/secret-id/lookup`، أي منحة `auth/*` يمنعها قسم «ما لا يُمنَح عمداً» في `deploy/vault/app-policy.hcl` («التطبيق لا يُدير Vault قطّ»)، **ويضع `secret_id` نفسه على السلك في كلّ كشطة**. الإنذار المسبق يخصّ فحصاً من جهة مشغّل Vault، أو البديل (أ)، لا نقطةَ مقاييس التطبيق.
- **ولماذا مقياسٌ لا فحصُ جاهزيّة**: `/health/ready` لا يسبر أيّ تبعيّة عمداً (§3.75) — جعلُه يسبر Vault يعكس ذلك القرار ويُحوّل عطباً صامتاً إلى **رفرفةٍ** تُخرِج الحاوية من الموازِن عند أوّل ومضة شبكة.

> 🔴 **⚠️ تفاعلٌ يجب أن يعرفه من يُضيف الكاشط: السبر نفسه يُبقي القفل مشتعلاً.** `VaultSecrets._call` يُعيد المصادقة مرّةً عند 403/401 — وهو **نافعٌ** في الحالة المستقرّة (‏`token_ttl=1h` بلا تجديد، فالكشطة تُجدّد الجلسة بدل أن يدفع الثمنَ أوّلُ طلبٍ حقيقيّ). لكن حين يكون **`secret_id` نفسه** ميّتاً تصير **كلّ كشطةٍ محاولةَ دخولٍ فاشلة**، فيُعاد إشعال قفل المستخدم الموصوف أعلاه بلا توقّف، ويبدو السرّ الجديد الصحيح مرفوضاً إلى الأبد. **لا تخزينَ مؤقّتاً يُلطّف هذا** عمداً: مذهب `/metrics` كلّه أن لا شيء يبقى بين الطلبات لأنّ `WEB_CONCURRENCY=2` يعني عمليّاتٍ شقيقة (جذر P0‑2، §3.81). وهو **مقبولٌ اليوم** لسببٍ مقيس: **لا كاشطَ يقرأ هذه النقطة أصلاً** — لا خدمة Prometheus في `docker-compose.yml` ولا في صورة RunPod، عمداً. ⇒ **من يُضيف الكاشط يرث القاعدة: أوقف الكاشط مع `app` قبل فكّ القفل والسكّ** — لا `stop app` وحدها. الترتيب كاملاً مكتوبٌ في `annotations.response` داخل `deploy/prometheus/alerts.yml`.

### 3.1‑ب Redis: تبعيّة إقلاعٍ صلبة أيضاً (ن‑1 · `release-blockers-plan.md §5‑ب` · قرارٌ: تثبيتها عمداً)

Vault ليست البنية التحتية الوحيدة التي يُجهض غيابُها الإقلاع كلّه — Redis كذلك، منذ الخطوة 2 (§3.81)، بلا أن يكون ذلك بنداً مقصوداً وقتها.

**أين يفشل بالضبط، مقيسٌ من الكود لا مُفترَض:** `_make_lifespan` (`src/app/api/main.py`) توصل `root.sweep_stale_notify_groups` **أوّل** عناصر `startup=` (قبل `hub.start_renewal`/`connect_storage`)، وعقدها صريحٌ في نفس الدالّة: «‏hook يرفع يُجهض الإقلاع بالكامل» — سابقة `connect_storage`/Vault نفسها. تلك الدالّة تستدعي `RedisStreamsConsumer.list_groups` (‏`XINFO GROUPS`) على كلّ مجرى إشعار، والمحوّل (`src/app/infrastructure/messaging/redis_streams.py`) يبتلع `ResponseError` الخاصّ بـ«‏no such key» وحده (‏= مجرًى لم يُنشأ بعد ⇒ `[]`)، بينما أيّ `ConnectionError`/`TimeoutError` حقيقيّ (Redis غير متاحٍ لحظة الإقلاع) **يُلتقَط ويُترجَم ثمّ يُعاد رفعه** عبر `except (RedisError, OSError)` → `raise _translate_consume(exc) from exc`، فيصعد عبر `sweep_stale_notify_groups` ثمّ عبر حلقة `startup=` فيقتل `lifespan` **قبل** أن يصل `app.state.ready = True` سطراً واحداً. لا استجابةٌ جزئيّة ولا تحذير — التطبيق **لا يُقلع أصلاً**.

> 🔴 **وهنا الفخّ التشخيصيّ، وهو ما يجعل هذا القسم يستحقّ القراءة قبل الحادثة لا بعدها:** `_translate_consume` (`redis_streams.py:450`) **يطرح تفاصيل العطب الأصليّ بالكامل** ويعيد `AppError("event consume failed", code="common.internal")` ثابتةً. فالسطر الأعلى في أثر التتبّع عند فشل الإقلاع بسبب Redis هو `event consume failed` / `common.internal` — رسالةٌ عامّةٌ **لا تذكر Redis ولا الشبكة إطلاقاً**. سبب العطب الحقيقيّ محفوظٌ في `__cause__` وحده بفضل `from exc`، أي **أسفل** أثر التتبّع تحت سطر «‏The above exception was the direct cause of…». ⇒ عند التشخيص **اقرأ أثر التتبّع كاملاً حتّى قاعه**؛ الاكتفاء بالسطر الأخير يُخفي المتّهم.

**القرار (مُتَّخَذٌ لا مُداوَلٌ هنا؛ لا تليينَ في الكود):** تثبيتها عمداً. تطبيقٌ بلا Redis نصفُ حيٍّ على أيّ حال — المجاري (`stream.*`)، الذاكرة المؤقّتة، وسقف WS العالميّ (الخطوة 11) كلّها فوقها — والاتّساق مع سياسة «الفشل الصادق عند الإقلاع» القائمة أصلاً لـVault أنفع من استثناءٍ يحتاج شرحاً منفصلاً كلّما رُوجعت السياسة. **هذا القسم توثيقٌ فقط** — لا تعديل على `sweep_stale_notify_groups`/`_make_lifespan`/`list_groups`.

> ⚠️ **عرَض عطبٍ يُشبه Vault ظاهريّاً**: حاوية `app` تدخل حلقة إعادة تشغيلٍ فور الإقلاع بلا الوصول إلى `/health` مطلقاً. راجع `docker compose ps redis` أوّلاً ثمّ سجلّ `app`. **لا تتوقّع رسالة Redis في أعلى الأثر** — أعلاه `AppError: event consume failed [common.internal]` كما شُرح أعلاه؛ الدليل القاطع هو `ConnectionError`/`TimeoutError` من `redis.asyncio` في **قاع** الأثر (`__cause__`). ما يميّزها فوراً عن عطب Vault: هذه لا تذكر «secret does not exist in Vault» (§8 أدناه) رغم تطابق شكل حلقة إعادة التشغيل بين الحالتين.
>
> **ملاحظة توثيقيّة:** لا يوجد في `docs/design/` قسمٌ مخصّص لتبعيّات الإقلاع غير هذه الوثيقة نفسها (`06-domain-models.md` — المُشار إليه في تكليف هذه الخطوة — يصف النطاق/التجميعات لا البنية التحتية)؛ فهذا القسم هو موضع التوثيق الوحيد المناسب.

### 3.2 شهادة TLS
`nginx-certs` يولّد `deploy/nginx/certs/{server.crt,server.key}` موقَّعةً ذاتيّاً (SAN: `localhost`, `127.0.0.1`) بـ`openssl` من صورة nginx نفسها. **مُتَجاهَلٌ في git.** الخطوة **لا تُعيد التوليد** إن وُجد ملفّان — وهي أيضاً طريقة تركيب شهادةٍ حقيقيّة: ضعها في المسارين وستتنحّى الخدمة.

`:80` يبقى يخدم ولا يُحوَّل إلى `:443` محليّاً (شهادةٌ موقَّعةٌ ذاتيّاً ⇒ احتكاكٌ بلا مكسبٍ أمنيّ على واجهة loopback). النشر العامّ **ينبغي** أن يحوّل، بسطرٍ واحد في `nginx.conf` مع **استثناء `/health`**: مِسبار موازِن حملٍ يطارد تحويلاً عبر TLS طريقةٌ معروفة لجعل خلفيّةٍ سليمة تبدو معطوبة.

> ⚠️ **لا ترويسة HSTS محليّاً، وغيابها قرار.** المتصفّح يطبّق HSTS **لكلّ مضيف** لا لكلّ منفذٍ أو تطبيق، فإرسالها من حافّة تطويرٍ على `localhost` يجبر **كلّ مشروعٍ آخر** يعمل على localhost على HTTPS طوال `max-age` بلا تراجعٍ إلّا بمسح حالة المتصفّح.
>
> **P1‑7 (خطوة 9) جعل هذا إعداداً حقيقيّاً لا تعليقاً فقط**، مع بقاء الاستبعاد المحلّي: `nginx.conf` يحمل `map $host $hsts_header { default ""; }` — إدخالٌ فارغٌ لكلّ مضيفٍ لم يُسمَّ صراحةً، و`add_header` **يُسقط الترويسة كليّاً** حين تكون قيمتها فارغة (مُتحقَّقٌ حيّاً على `nginx:1.27`، `docs/log/3.88.md`) — غيابٌ حقيقيّ لا قيمةً فارغة. نشرٌ حقيقيٌّ بمضيفٍ ثابتٍ يضيف سطراً واحداً في الخريطة (`deploy-linux-server.md §10.3`).

### 3.2‑ب حدّ المعدّل وترويسات الأمان وCORS (P1‑7، خطوة 9)
- **حدّ المعدّل**: `limit_req_zone`/`limit_conn_zone` في `nginx.conf` (مفتاحٌ `$binary_remote_addr`، مُتحقَّقٌ حيّاً أنّه العنوان الحقيقيّ للعميل الخارجيّ على هذه الطوبولوجيا — اتّصال نفس المضيف فقط يُصاب بـhairpin NAT إلى بوّابة الشبكة الداخليّة `172.18.0.1`). `location /` تحمل `limit_req` (20 طلب/ث، دفعة 40)، `/api/v1/ws` تحمل `limit_conn` فقط (100 اتّصالٍ متزامن/عنوان — اتّصالٌ طويلٌ لا طلبٌ متكرّر)، و`/health` **مُستبعدةٌ كليّاً** من كليهما (فحصٌ كلّ 10 ثوانٍ لا يحتمل حدّاً). رفضٌ عند هذه الحافّة يعيد **429** (`limit_req_status`/`limit_conn_status`) لا 503 الافتراضيّة — لكنّ الجسم صفحة nginx الافتراضيّة لا `problem+json` (هذه الطبقة لا تصل التطبيق فلا تملك `correlation_id`).
- **ترويسات الأمان**: `X-Content-Type-Options: nosniff` · `Referrer-Policy: strict-origin-when-cross-origin` · `X-Frame-Options: DENY`، على مستوى `http` في `nginx.conf` فتصل كل استجابة عبر الخادمين بلا ازدواج.
- **CORS**: nginx تسمح صراحةً بـFirebase Hosting (`aizzak-agent.web.app` و`aizzak-agent.firebaseapp.com`) و`http://localhost:5173` للتطوير، وتردّ على preflight؛ لا wildcard ولا `CORSMiddleware`. التفصيل في `03-api-spec.md §5`.
- **المساران متّفقان**: `deploy/nginx/{nginx.conf,app-locations.conf}` و`deploy/runpod/nginx.conf` يحملان نفس المناطق والقيم والترويسات (الأخير مكرَّرٌ حرفياً لا `include`، إذ لا ملفٍّ ثانٍ فيه).

### 3.3 الهجرات والمنح
> ⚠️ `alembic upgrade head` **ليس أمراً صالحاً هنا**: v1 يشغّل إحدى عشرة سلسلة مستقلّة (`DAT-03` — `version_table_schema` لكلّ وحدة)، فـ`head` غامضٌ وAlembic يرفضه بـ«Multiple head revisions are present». التسلسل الحقيقيّ (`platform@head` ثمّ `-x vts=<وحدة> upgrade <وحدة>@head` لكلّ وحدة) مُرمَّزٌ في `app/ops/provision.py`، وهي أيضاً موضع المنح — فالمنح خطوةٌ تشغيليّة لا DDL (`01 §6`)، ولا هجرةَ تُصدرها.

```bash
docker compose up migrate      # = python -m app.ops.provision (بدور aizzak_owner، مباشرةً إلى postgres لا عبر المجمّع)
```
الأدوار السبعة (`aizzak_owner` · `app_rw` · `outbox_relay` · `retention_sweeper` · `metrics_reader` · `transit_rotator` · `workspace_purger`، الأخير أُضيف مع BE-ADM-014) تُنشأ قبل ذلك عند **تهيئة العنقود** (`deploy/postgres/initdb/10-roles.sh`) لأنّ `CREATE ROLE` صلاحيّةُ عنقودٍ لا يملكها `aizzak_owner` عمداً. `provision` **يتحقّق** من وجودها ويفشل برسالةٍ تسمّي الخطوة الغائبة بدل أن يموت في المنتصف.

### 3.3‑ب ✅ ترقية عنقودٍ **قائم** — الأدوار الثلاثة الغائبة (ن‑9 · `p1-hardening-plan.md §5‑ب`)

> ✅ **نُفِّذ فعليّاً على العنقود الحيّ 2026‑07‑31** في نافذة نشرٍ بإذنٍ صريح — [§3.97](../log/3.97.md). ما يلي هو الإجراء **بعد** أن صحّحه التنفيذ: حمل النصّ الأوّل خمسة أخطاءٍ لم يكن أيٌّ منها ليظهر بالقراءة، أخطرُها التحذير المؤطَّر في الخطوة 0. اقرأ الخطوات الأربع **بالترتيب**؛ ليست مستقلّة.

`10-roles.sh` أعلاه يعمل **مرّةً واحدةً فقط** — عند تهيئة حجم `postgres` **الأوّل**. عنقودٌ أُنشئ **قبل** الخطوات 8/10/12 (‏`retention_sweeper`/`metrics_reader`/`transit_rotator` على التوالي) لا يُعاد تشغيل هذا السكربت عليه تلقائيّاً أبداً، فالأدوار الثلاثة تبقى **غائبةً** عنه — و`app.ops.provision`'s `_require_roles` يفحص **خمسة** أدوارٍ قبل أيّ هجرة (‏`provision.py:311`: `APP_ROLE`، `RELAY_ROLE`، `RETENTION_ROLE`، `METRICS_ROLE`، `TRANSIT_ROTATOR_ROLE` — الأدوار الستّة هي ما يُنشئه `10-roles.sh`، و`aizzak_owner` ليس منها لأنّه الدور المتّصل نفسه)، فيخرج بـ`SystemExit` يسمّي الثلاثة الغائبة تحديداً على عنقودٍ كهذا.

**⓪ قبل أيّ شيء — تحقّق من أنّ الأسرار لها قيمٌ حقيقيّة.** `TRANSIT_ROTATOR_PASSWORD` وُجد في `.env` الحيّة **placeholder** (`change-me-*`) يوم التنفيذ، رغم أنّ الخطوة 12 وصّلت المتغيّر في مواضعه الخمسة كلّها: وصّلت الاسم ولم يُعطه أحدٌ قيمة. **ولا حارسَ يكشف هذا** — `.env` غير متعقَّبةٍ في git، فلا اختبارَ يراها ولا CI، وحارس `:?` في Compose يرفض الفارغ لا `change-me-*`. الفحص الوحيد هو الطول، ولا تطبع القيمة. الحلقة تمرّ على **الثمانية كلّها** لا على الثلاثة الجديدة وحدها — انحرافُ سرٍّ قديمٍ يظهر بالكلفة نفسها:

```bash
for v in POSTGRES_SUPERUSER_PASSWORD AIZZAK_OWNER_PASSWORD APP_RW_PASSWORD \
         OUTBOX_RELAY_PASSWORD RETENTION_SWEEPER_PASSWORD METRICS_READER_PASSWORD \
         TRANSIT_ROTATOR_PASSWORD MINIO_ROOT_PASSWORD; do
  l=$(grep "^${v}=" .env); l=${l#*=}; printf "%-28s len=%s\n" "$v" "${#l}"   # 32، ولا يبدأ بـchange-me
done
grep "^MINIO_ROOT_USER=" .env   # معرّفٌ لا سرّ: لا قاعدةَ طولٍ عليه، لكن لا يبقى change-me-* أيضاً
```

> الثلاثة الجديدة (`RETENTION_SWEEPER` · `METRICS_READER` · `TRANSIT_ROTATOR`) هي التي تُستهلك في الخطوة ① أدناه؛ الخمسة الباقية تُقرأ **للتحقّق فقط**. لا تُصلح هنا ما تجده منحرفاً منها: تعديلُ أيٍّ من كلمات مرور Postgres في `.env` يغيّر بصمة إعداد `postgres` — وهو بالضبط الفخّ الموصوف تحت الخطوة ③ — و`MINIO_ROOT_PASSWORD` يفعل الشيء نفسه بخدمة `minio` **وبنسخة Vault منه** (`secret/minio`) التي يقرؤها `src/` فعليّاً — فتغييرُه نافذةُ عملٍ قائمةٌ بذاتها، لا سطرٌ يُدَسّ في منتصف ترقيةٍ للأدوار.

**① الأدوار — بصلاحيّة المستخدم الخارق فقط** (`aizzak_owner` بلا `CREATEROLE` عمداً؛ هذا بالضبط الفصل الذي يفرضه `10-roles.sh` نفسه). الأوامر أدناه **مُشتقّةٌ حرفيّاً** من ذلك الملفّ، لا من الذاكرة — استبدل قيم `change-me-*` بأسرارٍ حقيقيّة قبل أيّ تنفيذٍ فعليّ:

```sql
-- 1) الأدوار الثلاثة -- نفس الشكل الحرفيّ في 10-roles.sh (LOGIN NOINHERIT، لا CREATEROLE):
CREATE ROLE retention_sweeper LOGIN NOINHERIT;
CREATE ROLE metrics_reader    LOGIN NOINHERIT;
CREATE ROLE transit_rotator   LOGIN NOINHERIT;

-- 2) كلمات المرور -- بأسرارٍ حقيقيّة، لا الأمثلة التالية للـ.env.example حرفياً:
ALTER ROLE retention_sweeper PASSWORD 'change-me-retention';
ALTER ROLE metrics_reader    PASSWORD 'change-me-metrics';
ALTER ROLE transit_rotator   PASSWORD 'change-me-rotator';

-- 3) الاتّصال بقاعدة البيانات وحده -- المنح على الجداول تأتي من app.ops.provision، لا من هنا
--    (استبدل aizzak إن اختلف اسم قاعدتك عن ${POSTGRES_DB}):
GRANT CONNECT ON DATABASE aizzak TO retention_sweeper, metrics_reader, transit_rotator;
```

**② ابنِ الصورة أوّلاً — وإلّا كان الإغلاق زائفاً.** عنقودٌ متأخّرٌ عن المستودع تكون صورتُه متأخّرةً معه بالضرورة (كانت متأخّرةً **ثمانية التزامات** يوم التنفيذ). و`docker compose up migrate` **لا يعيد بناء صورةٍ قائمة** — ن‑4، §3.0 أعلاه — فيشغّل `provision.py` **القديم**: لا يعرف الهجرات الجديدة ولا المنح ولا الأدوار الخمسة، فيخرج بنجاحٍ وقد فعل لا شيء. وهذه أخطر صور الفشل: بوّابةٌ خضراء لا تُثبت شيئاً.

```bash
docker compose build migrate   # ن-4: بلا هذا يعمل provision البائت بنجاحٍ كاذب
```

**③ ثمّ المنح على الجداول + الهجرات المتبقّية** — نفس أمر §3.3 أعلاه، **زائداً `--no-deps`**:

```bash
docker compose up --no-deps migrate      # = python -m app.ops.provision
```

> 🔴 **`--no-deps` ليست تحسيناً — بدونها يُعاد إنشاء `postgres`.** `TRANSIT_ROTATOR_PASSWORD` (‏و`RETENTION_SWEEPER_PASSWORD` و`METRICS_READER_PASSWORD` معها) عناصرُ في **بيئة خدمة `postgres`** (`docker-compose.yml:117/124/133`). فالخطوة ⓪ حين تُعطي أيّاً منها قيمةً حقيقيّة في `.env` **تغيّر بصمة إعداد `postgres`**؛ و`docker compose up migrate` يبدأ التبعيّات، فيرى `postgres` «قديماً» فيُعيد إنشاءه. أي أنّ مشغّلاً يتبع هذا القسم **بترتيبه المكتوب** يُسقط قاعدة بياناته وهو يظنّ أنّه يشغّل هجرة. قاعدة البيانات صحّيّةٌ سلفاً في هذا السيناريو بحكم التعريف، فلا شيء يحتاج البدء.

> ✅ **منحة `transit/rewrap/tenant-secrets` وصلت Vault الحيّ سلفاً — لا تُعِد تشغيل `vault-bootstrap` لأجلها.** حمل هذا الموضع تحذيراً بأنّها «لا تصل إلّا بإعادة تشغيل `vault-bootstrap`»؛ وقراءةُ سياسة `app` من الخادم الحيّ يوم التنفيذ أظهرت المسار **موجوداً فيها**. السبب أنّ علاج ن‑10/ن‑11 (‏[§3.94](../log/3.94.md)) أعاد تشغيل تلك الخدمة، وهي تكتب السياسة في **كلّ** تشغيل (`bootstrap.sh`: `vault policy write app /app-policy.hcl`). **وهذا يستحقّ البقاء مكتوباً**: إعادةُ تشغيل `vault-bootstrap` هي نفسها ما محا تدوير ن‑11 بصمتٍ من قبل (تُعيد كتابة `secret/db` من `.env`)، فاتّباعُ التحذير البائت كان سيُدخل أخطر عمليّةٍ ممكنةٍ في هذه النافذة بلا حاجة. **تحقّق قبل أن تُقرّر** — والقراءة رخيصة:
>
> ```bash
> docker compose exec -T vault sh -c 'VAULT_ADDR=http://127.0.0.1:8200 \
>   VAULT_TOKEN=$(sed -n "/root_token/p" /vault/init/init.json | sed "s/.*\"root_token\": *\"\([^\"]*\)\".*/\1/") \
>   vault policy read app' | grep '^path'

**④ تحقّق.** سبعةُ أدوار · الرؤوس تقدّمت · السياسات والفهارس موجودة · `metrics_reader` يسجّل دخولاً **عبر PgBouncer** (‏النقطة الوحيدة القادرة على إفشال ترقية `app` لاحقاً، فاختبرها الآن) · `app_rw` ما يزال `INSERT` وحده على `platform.outbox` · الحاويات لم تُعَد. التفصيل الكامل بالأرقام في [§3.97](../log/3.97.md) §4.

### 3.4 ⚠️ Vault دائمٌ الآن، وهذا لا يُغنى عن قراءته (release-blockers-plan.md §3 خطوة 1)

**القرار القائم حتّى §3.79 كان `vault server -dev` — في الذاكرة بالكامل.** إعادة تشغيل الحاوية كانت تمحو KV والTransit وAppRole معاً، و**الخطر الحقيقيّ لم يكن التوقّف بل أنّ مفتاح Transit المُعاد توليده لا يفكّ تعمية ما عُمّي بالمفتاح القديم** — فقدٌ دائمٌ لأوّل اعتماد مستأجرٍ أو رمز OAuth يُخزَّن. هذا **أُصلح جذريّاً لا تعافياً أسرع**: `storage "file"` على حجمين مُسمَّيَين دائمين.

**البنية الآن:**

- `vault-data` — ما يملكه Vault نفسه (‏KV v2 + Transit + AppRole).
- `vault-init` — مفتاح فكّ الختم + التوكن الجذر، **حجمٌ منفصلٌ عمداً** عن `vault-data` (المتطلّب 2 في الخطوة): بيانات Vault تبقى بيانات Vault وحدها، ومادّة التهيئة التي تفتحها منفصلةٌ عنها.
- `deploy/vault/start.sh` **يستبدل** `docker-entrypoint.sh` الافتراضيّ للصورة: يشغّل `vault server` بنفسه، ثمّ يقوده خلال `operator init` (أوّل إقلاعٍ فقط، `key-shares=1`/`key-threshold=1`) أو `operator unseal` (كلّ إقلاعٍ بعده، من الملفّ المسجَّل) — **قبل** أن يستطيع فحص الصحّة الإبلاغ بالنجاح. `vault status` — مقيسٌ حيّاً على هذه الصورة (`hashicorp/vault:1.18`) — يخرج بـ`1` وهو غير مستمعٍ بعد، `2` وهو مختوم، و`0` فقط حين يُفكّ الختم؛ فحص الصحّة (`test: ["CMD", "vault", "status", ...]`) لم يتغيّر حرفاً، لكنّ معناه صار **أدقّ**: مختومٌ ⇒ غير صحّي، تماماً كما يفترض `depends_on: {condition: service_healthy}` لكلّ مستهلكٍ آخر في هذا الملفّ.

**ما تغيّر عمليّاً:**

```bash
docker compose restart vault    # لا يمحو شيئاً بعد الآن
```

KV والTransit وAppRole **تبقى**. مفتاح Transit **نفسه** — لا يتجدّد؛ مُثبَتٌ حيّاً في `release-blockers-plan.md` §4 (نفس زمن الإنشاء ونفس رقم الإصدار قبل إعادة التشغيل وبعدها، وتعمية/فكّ عبر إعادة التشغيل ناجحان بنفس المفتاح). القاعدة القديمة «`docker compose up -d` لا `docker start`» **لم تعد ضروريّةً لهذا السبب بالذات** — الحاويّة نفسها تتعافى ذاتيّاً عبر `start.sh` أيّاً كانت طريقة إعادة تشغيلها.

**⚠️ لكنّ هذا وحده غير كافٍ لإنتاجٍ حقيقيّ، وهذا مقصودٌ لا سهو.** لا يوجد KMS محلّيّاً يُفكّ الختم عبره تلقائيّاً بأمان، فمفتاح فكّ الختم والتوكن الجذر يُكتَبان في ملفٍّ نصّيٍّ عاديّ على حجم `vault-init` (`chmod 600`). أيّ من يصل ذلك الحجم — نسخةً احتياطيّةً لم تُشفَّر، أو جذر المضيف — يستطيع فكّ ختم Vault وقراءة **كلّ** سرٍّ يحرسه. **مقبولٌ لمضيفٍ واحدٍ محلّيّ فقط، وغير مقبولٍ إطلاقاً لإنتاجٍ حقيقيّ.** مسار الترقية — auto-unseal عبر KMS خارجيّ (`seal "awskms"`/`"gcpckms"`/`"azurekeyvault"`) أو Transit auto-unseal عبر مثيل Vault آخر خارج هذا المضيف — يحتاج تلك الخدمة موجودةً مسبقاً، ولذلك **وُصف ولم يُنفَّذ**؛ التفصيل والنسخ الاحتياطيّ/الاستعادة في `docs/quickstart.md §5.2`.

**إن فُقد `vault-init` بينما `vault-data` سليم:** `start.sh` **يرفض** محاولة `operator init` جديدة (ستُنشئ مفتاحاً منفصلاً لا يفتح البيانات القائمة) ويفشل بصريحٍ يشرح ذلك في سجلّ الحاوية. لا علاجَ آليّ — استعادة `init.json` من نسخةٍ احتياطيّة هي السبيل الوحيد.

> `VAULT_ROLE_ID` محليّاً **مثبَّت** (‏`AIZZAK_APPROLE_ROLE_ID`) لأنّ الدور يُنشأ بمعرّفٍ عشوائيّ في **أوّل** إقلاعٍ فقط الآن (لا في كلّ إقلاعٍ كما في وضع dev)؛ التثبيت يمنع أن يتقادم `.env` بصمتٍ لو أُعيد إنشاء الدور يوماً (حجمٌ نظيف، مثلاً). القيمة غير سرّية (`05 §2`). في نشرٍ حقيقيّ: لا تثبّتها، واقرأ المولَّد مرّةً.

> ✅ **ترتيب الإقلاع لم يعد قاعدةً يدويّة** (كان درس 5.1‑ج، §3.46). مجموعات المستهلكين ما تزال تُنشأ عند `$` (ذيل المجرى، `redis_streams.py:235` — لم يتغيّر)، وهذا بالذات هو ما كان يجعل مجموعةً تُنشأ **بعد** نشرٍ على مجرى جديد لا ترى تلك المدخلات أبداً. لكن منذ [§3.107](../log/3.107.md) صار `build_relay_from_env` (‏`workers/bootstrap.py`) يعيد إغلاق `ensure_topology()` يمرّ على `STATIC_CONSUMER_TOPOLOGY` (‏`framework/events/topology.py`) قبل أن يبدأ `outbox_relay.py::run` النشر — فلا مسار إقلاعٍ (Compose أو RunPod أو `python -m` مجرّد) يصل أوّل `XADD` قبل أن تُنشأ المجموعات الأربع كلّها. **العامل لم يعد يحتاج أن يسبق المُرحّل** — الضمان صار داخل عمليّة المُرحّل نفسها، لا في ترتيب إقلاع خدمتين. مُثبَتٌ حيّاً على Redis حقيقيّ في [§3.108](../log/3.108.md).

### 4.1 ⚠️ طول المجاري — `XACK` **لا يحذف**
مجاري Redis سجلٌّ **إلحاقيّ**: `XACK` يمسح قائمة المعلّق لمجموعةٍ ولا يحذف المدخلة. فـ`stream.<وحدة>` ينمو بلا حدّ **حتّى مع عمّالٍ أصحّاء يُقرّون كلّ شيء** — لا فقط بينما 7.2 محجوزة. وRedis هنا مقيسٌ على `maxmemory 0` وسياسة `noeviction`: **لا سقف في أيّ طبقة**.

العلاج المُنفَّذ: `XADD ... MAXLEN ~ N` عبر `STREAM_MAXLEN` (افتراضيّ **100000**؛ `0` يعطّل القصّ = سلوك ما قبل 7.3 حرفيّاً). التقريب (`~`) مقصود: القصّ الدقيق يجعل كلّ `XADD` — وهو المسار الساخن لكلّ حدثٍ في المنصّة — يدفع حذفاً بتعقيد O(n) لأجل حدٍّ لا رأي لأحدٍ في قيمته بالضبط.

> ⚠️ **المقايضة**: القصّ قد يُسقط مدخلاتٍ لم يقرأها مستهلكٌ متعثّر، وصفّ الـoutbox يكون قد وُسم `published` سلفاً ⇒ **فقدٌ حقيقيّ لا إعادة تسليم**. لذلك الافتراضيّ سخيٌّ لا ضيّق، ولذلك §7 يطلب مراقبة `XLEN` بدل معاملة السقف كحلّ.

### 4.2 أداة DLQ — `python -m app.ops.dlq` (‏P1‑4 · `p1-hardening-plan.md` §3 خطوة 7)

مدخلة الرسالة إلى `<stream>.dlq` (‏`RedisStreamsConsumer.dead_letter`، §4.1) كانت بلا مخرج: قبل هذه الأداة لا شيء تحت `python -m app.ops.*` يقرأها أو يعيد حقنها، والوحيد المتاح كان `redis-cli` يدويّاً. ثلاثة أفعال فقط:

```bash
python -m app.ops.dlq peek stream.knowledge [--count N]                  # قراءةٌ بلا استهلاك (XRANGE)
python -m app.ops.dlq requeue stream.knowledge <dlq-entry-id> [...]      # نسخ `ce` إلى المجرى الأصليّ
python -m app.ops.dlq purge stream.knowledge <dlq-entry-id> [...] --yes # XDEL — لا رجعة، ويرفض بلا `--yes`
```

`<stream>` هو اسم **المجرى الأصليّ** (مثل `stream.knowledge`)، لا لاحقة `.dlq` — كلّ فعلٍ يبنيها بنفسه.

> ⚠️ **مدخلةٌ بلا `ce` غير قابلةٍ لإعادة الحقن أصلاً.** حقل `reinjectable` في مخرجات `peek` يُفرّق الصنفين: مدخلةٌ دخلت DLQ بالسبب `malformed_envelope` لعدم وجود حقل `ce` إطلاقاً (بايتاتٌ سامّة من خارج مسار المنتِج) لا بايتات لديها لتُحفَظ — و`requeue` يرفضها بخطأٍ يسمّي المدخلة والسبب، لا بفشلٍ صامت أو استثناءٍ مبهم.

> ⚠️ **إعادة الحقن ليست عمياء عن `platform.processed_events`، والأداة لا تراها أصلاً.** مطالبة DD‑09 تُسجَّل في نفس معاملة الأثر (`uow.begin`)، فتلتزم أو تتراجع معاً؛ ولذلك أيّ رسالةٍ تصل DLQ بسبب `handler_failed` لم يلتزم ادّعاؤها قطّ (كلّ محاولةٍ فشلت تراجعت بمعاملتها) — فإعادة حقنها تُعالِج كاملةً وبأمان. لكنّ إعادة حقن **نفس** مدخلة DLQ مرّتين دون `purge` بينهما (أو رسالةٌ أُعيدت معالجتها مسبقاً بمسارٍ آخر) تجد الادّعاء ملتزماً بالفعل ⇒ المعالج يتجاهلها بهدوءٍ (تكرارٌ نظيف) والمحرّك يُقرّها — أداةٌ بلا منفذ Postgres لا تستطيع تمييز الحالتين، وهذا مُعلَنٌ في مصدر الأداة (`src/app/ops/dlq.py`) لا مُختَرَعٌ حلٌّ له.

### 4.2‑ب أداة مجموعات الإشعار اليتيمة — `python -m app.ops.notify_groups` (‏[§3.135](../log/3.135.md))

```bash
python -m app.ops.notify_groups list                       # قراءةٌ محضة: كلّ مجموعة cg.notify مع LIVE/ORPHAN وسببه
python -m app.ops.notify_groups sweep --yes                # XGROUP DESTROY لليتيمة — لا رجعة، ويرفض بلا `--yes`
python -m app.ops.notify_groups sweep --yes --settle-seconds 0   # يتخطّى القراءة الثانية (بيئةٌ موقوفة/اختبار)
```

**العطب الذي تسدّه، وهو ليس خطأً في الكانس القائم بل نتيجةٌ حتميّة لحارسه الأوّل.** `_sweep_stale_notify_groups` (‏`framework/di/composition_root.py`) يكنس المجموعات اليتيمة عند إقلاع API، **ولا يفحص إلّا ما يبدأ باسم مضيفه هو** — عمداً، كي لا تمسّ نسخةٌ مجموعاتِ نسخةٍ أخرى مهما تصادمت أرقام العمليّات. لكنّ إعادة إنشاء الحاوية تمنحها **اسم مضيفٍ جديداً**، فتصير مجموعات الحاوية السابقة مُسمّاةً بمضيفٍ لن يُقلع أبداً: **لا شيء في المنظومة مخوَّلٌ بكنسها، لأنّ الوحيد المخوَّل مات**. تتراكم رتيباً — قِيست 2026‑08‑13 على المكدّس المحلّيّ: **20 مجموعةً يتيمة** على مجريين، من خمسة مضيفين موتى، كلّها `pending 0`.

> ⭐ **ولماذا أداةٌ يستدعيها المشغّل لا كنسٌ تلقائيّ:** حياةُ عمليّةٍ على مضيفٍ **آخر** غير قابلةٍ للبتّ من هنا — لا جدول عمليّاتٍ نسأله، وهذا بعينه سبب انحصار كانس الإقلاع في مضيفه. القابل للبتّ هو **هل يقرأ أحدٌ تحت هذه المجموعة الآن**، وعليه تقوم الأداة.
>
> 🔄 **وقد رُوجعت هذه الحيثيّة في [§3.137](../log/3.137.md)، لا نُقضت.** انحصارُ كانس الإقلاع في مضيفه يبقى صحيحاً ولم يُمَسّ. لكنّ ما تبتّه البوّابات الثلاث — «هل يقرأ أحدٌ الآن» — **لا يعتمد على المضيف أصلاً**، فصحّ تشغيله دوريّاً من أيّ نسخة: صارت القاعدة مهمّةً خلفيّةً في API كلّ `NOTIFY_GROUP_SWEEP_INTERVAL_S` (‏افتراضيّ 900 ث · `0` يُعطّل). **والقاعدة انتقلت** إلى `infrastructure/messaging/consumers/sweeper.py` ولم تُنسَخ: هذا الملفّ صار غلافاً رفيعاً فوقها، فالمشغّل والمهمّة يُطبّقان نصّاً واحداً. تبقى الأداة للفعل الفوريّ حين لا يُنتظَر المؤقّت.

**ثلاث بوّابات، كلٌّ منها ضروريّة، وكلٌّ مُثبَتٌ فشلُ الاختبار عند إسقاطها ([§3.135](../log/3.135.md)):** ‏(1) `consumers = 0` — قيدُ المستهلك يبقى بعد موت العمليّة، فوجوده يعني إمّا قارئاً حيّاً وإمّا مجموعةً ما تزال مستعملة، وكلاهما رفض · (2) `pending = 0` — مجموعةٌ تحتجز رسائل تملكها، وتدميرها يُسقط دفترها بصمت · (3) ليست عمليّةً حيّةً على **هذا** المضيف (‏`os.kill(pid, 0)`، للمضيف الوحيد الذي يمكن سؤاله).

> ⚠️ **ونافذة الاستقرار هي الفرق بين الأداة ومرشّحٍ من سطر.** جسرٌ أنشأ مجموعته للتوّ ولم يُصدر أوّل `XREADGROUP` بعد يُظهر صفر مستهلكين **للحظة**. وتدميرها حينها **أسوأ** من سباق الكانس القائم: تلك العمليّة تجاوزت `setup()` ولن تنادي `ensure_group` ثانيةً، فقراءتها التالية تفشل بـ`NOGROUP` بدل أن تُعيد الإنشاء بهدوء. لذلك تُشترط **قراءتان** يفصلهما `--settle-seconds` (افتراضيّ 5) تُظهران المجموعة غير مستعملةٍ في كلتيهما.

📌 **ولا تمسّ الأداة مجموعات الطوبولوجيا الثابتة** (`cg.knowledge` · `cg.media` · `cg.memory`) — تدمير إحداها يُعيد موضع تسليم وحدةٍ كاملةٍ إلى ذيل المجرى بصمت. ولا تحذف **مستهلكاً** خاملاً داخل مجموعةٍ حيّة: قاعدةُ أمانٍ أخرى (‏`pending > 0` ⇒ `XAUTOCLAIM` أوّلاً)، وآليّةٌ أخرى — §4.2‑ج أدناه.

### 4.2‑ج نسيانُ المستهلكين الموتى — آليّتان بلا مشغّل (‏[§3.137](../log/3.137.md) · ت‑2)

لا أمرَ هنا يُنسَخ ويُلصَق: هذه الطبقة **لا واجهةَ تشغيليّةَ لها عمداً**، لأنّ ما تفعله يجب أن يحدث في كلّ إعادة تشغيلٍ بلا أن يتذكّره أحد. المشغّل يضبط ثلاثة مفاتيح ويقرأ ثلاثة أسطر سجلّ.

**العطب الجذريّ لم يكن في Redis.** بايثون لا يُركّب معالجاً لـ`SIGTERM`، والتصرّف الافتراضيّ **إنهاءُ العمليّة فوراً** — فـ`docker compose stop`/`restart`/`up -d` (وكلّها تُرسل `SIGTERM` أوّلاً) كانت تقتل العامل بين تعليمتين، **ولا تُنفَّذ `finally` إطلاقاً**، رغم أنّ توثيق المداخل الثلاثة كان يقول عكس ذلك. فلا عميلٌ يُغلق، ولا قيدُ مستهلكٍ يُحذف: **شاهدةُ قبرٍ لكلّ إعادة إنشاء حاوية**.

| | `workers/lifecycle.py` | `consumers/sweeper.py` |
|---|---|---|
| المُشغِّل | `SIGTERM`/`SIGINT` | مؤقّتٌ داخل حلقة كلّ عاملٍ حيّ |
| الطبيعة | **مضبوطٌ وفوريّ** — العمليّة تعرف اسمها | **تقديريٌّ ومؤجَّل** — الخمول دليلٌ ظنّيّ |
| يُغطّي | الخروج النظيف وحده | `SIGKILL` · OOM · انقطاع الكهرباء |

**لا واحدةَ منهما تُغني عن الأخرى**، ولذلك بقيتا اثنتين.

```bash
CONSUMER_SWEEP_INTERVAL_S=300     # العمّال وحدهم: كم مرّةً يبحث الحيّ عن إخوةٍ موتى
CONSUMER_STALE_IDLE_S=900         # ⚠️ عتبةُ موتٍ لا إيقاع استطلاع — اقرأ أدناه
NOTIFY_GROUP_SWEEP_INTERVAL_S=900 # API وحدها: كنسُ cg.notify.* اليتيمة (§4.2‑ب)
```

> ⚠️ **`CONSUMER_STALE_IDLE_S` عتبةُ موت.** مستهلكٌ تجاوز خموله إيّاها **يُعلَن ميّتاً ويُحذف**. ساعةُ الخمول تُصفَّر كلّ `CONSUMER_BLOCK_MS` (5 ث) للعامل الفارغ، لكنّ معالجاً مشروعاً قد يعمل دقائق — فالقيمة تبقى بعيدةً عن الاثنين. قيمةٌ ضيّقةٌ **تحذف عمّالاً أحياء**، وهي عين آفة ت‑6 في صيغةٍ أشدّ.

> 🛡️ **ولا رسالةَ تُفقَد.** خاملٌ بـ`pending > 0` **لا يُحذف**: التسلسل `XAUTOCLAIM` إلى مستهلكٍ حيّ ⇒ إعادةُ قراءة `pending` ⇒ الحذف، **وإلّا الرفض والتسجيل**. وهذا ليس تنظيفاً فحسب: رسالةٌ عالقةٌ في دفتر مستهلكٍ ميّت **لا يُعاد تسليمها لأحدٍ أبداً** بدونه، لأنّ قراءة الاسترداد محصورةٌ باسم المستهلك الذي مات معه.

> 📌 **والكنس مُطفأٌ افتراضيّاً داخل المحرّك** (`sweep_interval_s = 0`)، ويُفعَّل في `workers/bootstrap.py` وحده. جسرُ الإشعارات في API يستعمل `StreamConsumer` نفسه، ولو كنس مستهلكين لجاز أن يحذف قيدَ جسرٍ حيّ في نسخةٍ أخرى **فتبدو مجموعتُه يتيمةً لكانس §4.2‑ب فتُدمَّر عليه**. الفصل بالبناء لا بالتعليق.

أسطر السجلّ التي تُقرأ: `consumers.sweep_deleted` (شبَحٌ أُزيل) · `consumers.sweep_reclaimed` (رسائل استُردّت) · `consumers.sweep_refused` (رفضٌ لأنّ قيداً نجا من الاسترداد — **يستحقّ نظرة**) · `worker.shutdown_signal` (خروجٌ نظيفٌ بدأ).

### 4.2‑د تقريرُ الـDLQ الدوريّ — بلا مشغّلٍ أيضاً (‏[§3.138](../log/3.138.md) · ت‑6)

أداةُ §4.2 كانت **كاملةً وصامتة**: تُجيب إجابةً ممتازة، ولا شيء يدفعك إلى سؤالها. قِيس أثرُ ذلك حرفيّاً — مدخلةٌ واحدة على `stream.memory.dlq` منذ **2026‑08‑03**، ما زالت هناك في **2026‑08‑15**، لم يُبلِّغ عنها شيءٌ في اثني عشر يوماً. فصار كلُّ عاملٍ يقرأ كلَّ `DLQ_WATCH_INTERVAL_S` طوابيرَ الرسائل الميتة **لمجاريه هو**، ويُصدر سطراً واحداً لكلّ طابورٍ غير فارغ:

```bash
DLQ_WATCH_INTERVAL_S=300          # العمّال وحدهم: كم مرّةً يُبلِّغ الحيُّ عن DLQ غير فارغ (0 يُعطّل التبليغ فقط)
docker compose logs worker-memory | grep dlq.backlog
```

سطرٌ واحدٌ يحمل ما يُتّخذ عليه القرار: `stream` · `depth` · `oldest_entry_id` · **`oldest_age_s`** · `oldest_reason` · و`triage` = الأمر الجاهز `python -m app.ops.dlq peek <stream>`.

> ⭐ **العمرُ هو المضمون، لا العدد.** ملاحظةُ ت‑6 الحادّة ليست «هناك مدخلة» بل أنّ **طابوراً غير فارغٍ دائماً يُصيّر «غير فارغ» هو الحالة الطبيعيّة في عينك** فتفقد الإشارة قيمتها. تقريرٌ يقول `depth=1` وحدها كان سيُعيد إنتاج العطب بأمانة؛ «‏`depth=1` عمرُها 12 يوماً» شيءٌ آخر تماماً.

> 🔇 **والصمت هو الحالة الصحّيّة.** طابورٌ فارغ **لا يُسجِّل شيئاً** — حياةُ الحلقة مغطّاةٌ أصلاً بنبض ت‑3 (`ops/healthcheck.py`)، وسطرُ «كلُّ شيءٍ على ما يرام» كلَّ خمس دقائق × ثلاثة عمّال هو بالضبط الضجيج الذي يجعل تحذيراً حقيقيّاً غير مقروء.

> 🛡️ **والنظرُ لا يستهلك أبداً.** `XLEN` + `XRANGE` بمدخلةٍ واحدة، ولا `XREADGROUP` ولا `XACK` ولا `XDEL` — قاعدةُ `peek` نفسها مطبَّقةً على قارئٍ آليّ، لأنّ مراقباً قادراً على تحريك مدخلةٍ قادرٌ على إضاعة ما جاء ليُبلِّغ عنه. وفشلُ القراءة يُسجَّل (`dlq_watch_failed`) ولا يُوقف الحلقة: التبليغ أقلُّ أهمّيّةً من الاستهلاك دائماً.

> ⚠️ **ولا مجموعةَ استهلاكٍ على مجاري الـDLQ — قراراً لا سهواً.** المجموعةُ تعني **مستهلكاً**، ومستهلكٌ آليٌّ للـDLQ له سلوكان لا ثالث لهما، وكلاهما خطأ: إعادةُ الحقن تلقائيّاً تُعيد تشغيل المعالج الذي فشل خمس مرّاتٍ أصلاً (حلقةُ سُمٍّ — المدخلةُ المقيسة أعلاه كانت ستُعالَج نحو 3400 مرّة)، وأيُّ تصريفٍ آخر حذفٌ بخطواتٍ إضافيّة. المستهلك الصحيح الوحيد لهذا الطابور **إنسانٌ بيده أداة §4.2**؛ فالناقص لم يكن مستهلكاً، بل من يُخبر الإنسان.

📌 **والمقياس الذي كان أعمى صار يرى:** `aizzak_dlq_depth` (‏§8 أدناه) كان يقرأ `stream.knowledge` و`stream.media` **فقط** — بينما المدخلةُ الوحيدة على المكدّس الحيّ كانت على `stream.memory.dlq`، أي على طابورٍ لا يقرؤه المقياس أصلاً. صار يشتقُّ قائمته من `framework/events/topology.py` (المصدر نفسه الذي تُزوَّد منه مجموعات الاستهلاك)، فلا يمكن لمجرىً أن يُستهلَك دون أن يُراقَب طابورُه.

### 4.3 أداة الاحتفاظ — `python -m app.ops.retention` (‏P1‑5 · `p1-hardening-plan.md` §3 خطوة 8)

ثلاثة جداولٍ تنمو بلا حدٍّ منذ إنشائها: `platform.processed_events` (مُوثَّقٌ صراحةً «لا سياسة احتفاظٍ في v1»، 01 §4.2)، `platform.idempotency_keys` (01 §4.2‑ب، نفس التوثيق)، وصفوف `platform.outbox` **المنشورة** (‏`published_at IS NOT NULL`). لا مكنسة ولا مهمّة دوريّة كانت موجودةً قبل هذه الخطوة.

```bash
python -m app.ops.retention sweep [--dry-run]                                         # الثلاثة معاً، كلٌّ بحدّه الافتراضيّ
python -m app.ops.retention sweep --table outbox [--older-than-days N] [--dry-run]     # جدولٌ واحد، حدٌّ مُتجاوَزٌ اختياريّاً
```

`--older-than-days` يتطلّب `--table` **دائماً** — لا يوجد تجاوزٌ واحدٌ يُطبَّق على الجداول الثلاثة معاً؛ أعمارها المفيدة مختلفة (أسفل). `--dry-run` يُحصي ما **كان سيُحذَف** (‏`SELECT count(*)` بنفس الشرط) ولا يحذف شيئاً.

**الحدود الافتراضيّة، ولماذا اختلفت:**
| الجدول | الحدّ | العلّة |
|---|---|---|
| `idempotency_keys` | يومان | غايتها الوحيدة الردّ على إعادة محاولة العميل **نفسه** لطلبٍ أرسله فعلاً (‏03 §0) — نافذةٌ تُحسَم بالساعات لا الأسابيع؛ وجسد الردّ المخزَّن بيانات مستأجرٍ فعليّة، فالتقصير أيضاً تقليلٌ للبيانات لا توفير تخزينٍ فقط. |
| `processed_events` | 30 يوماً | مفتاح تفريقٍ عارٍ بلا حمولة. نافذة التكرار الحقيقيّة في آليّات إعادة المحاولة الحاليّة تُقاس بالثواني (‏`consumer_block_ms=5000 × max_retries_before_dlq=5`)، لكنّ عمليّة إعادة حقنٍ يدويّةٍ عبر `app.ops.dlq requeue` (خطوة 7) قد تقع بعد أيّامٍ من الفشل الأصليّ — 30 يوماً هامشٌ سخيٌّ لكنّه محدود. |
| `outbox` (منشورةٌ فقط) | 90 يوماً | الصفّ هنا يحمل مظروف CloudEvents كاملاً + `correlation_id`/`causation_id` — قيمةٌ تحقيقيّةٌ حقيقيّة لمراجعة حادثةٍ لاحقة، فأُبقي عليه أطول الثلاثة، مع حدٍّ منتهٍ يظلّ يوقف النموّ. |

> ⭐ **التوتّر المعماريّ الذي حسمته هذه الخطوة، لا الذي تجاهلته.** `src/app/ops/provision.py` يمنح `app_rw` **`INSERT` وحدها** على `outbox`/`processed_events` عمداً — تعليلها الحرفيّ: «دورٌ لا يملك إلّا `INSERT` لا يستطيع سرد السجلّ ولا إلغاء معالجة حدثٍ لفرض إعادة تشغيل». منح `app_rw` صلاحية `DELETE` لإغلاق فجوة الاحتفاظ كان سيهدم بالضبط هذا الضمان. فبدل ذلك: دورٌ **رابعٌ** منفصل، `retention_sweeper` (نظير `outbox_relay` بالضبط)، يحمل `SELECT, DELETE` فقط على الجداول الثلاثة (‏`RETENTION_GRANTS`) — لا شيء يتيح له تزوير صفٍّ أو تعديله. وعلى `platform.idempotency_keys` تحديداً (الجدول الوحيد في `platform` بسياسة RLS) أضافت الهجرة `0003_retention_sweep.py` سياستين مسموحتين (permissive) مقصورتين على هذا الدور وحده (‏`retention_sweeper_select`/`retention_sweeper_delete`، بـ`USING (true)`) تتّحدان بمنطق **OR** مع `tenant_isolation` القائمة — فيصل المكنسة إلى كلّ مستأجرٍ في نداءٍ واحد، بينما يبقى حصر `app_rw` بمستأجره الحاليّ سليماً تماماً.

> ⚠️ **`DATABASE_URL` لهذه العمليّة يجب أن يكون DSN الخاصّ بـ`retention_sweeper`** — نفس اصطلاح كلّ عمليّةٍ بدورها الخاصّ الذي توثّقه `provision.py`/`workers/bootstrap.py` (‏`aizzak_owner` يهاجر، `app_rw` يُنتِج، `outbox_relay` ينشر، `retention_sweeper` يكنس؛ لا دورٌ يرتدي قبّعة دورٍ آخر).

> ✅ **الدور موصَّلٌ الآن بتهيئة العنقود الحقيقيّة** (نفس نمط `outbox_relay` حرفيّاً — لا نمط مخترَع): `deploy/postgres/initdb/10-roles.sh` ينشئ `retention_sweeper` (‏`CREATE ROLE ... LOGIN NOINHERIT` داخل نفس حارس `IF NOT EXISTS`، `ALTER ROLE ... PASSWORD`، `GRANT CONNECT`) · `docker-compose.yml` (خدمة `postgres`) يشترط `RETENTION_SWEEPER_PASSWORD: ${RETENTION_SWEEPER_PASSWORD:?...}` كما يشترط كلمات المرور الثلاث الأخرى · `.env.example`/`.env` يحملان `RETENTION_SWEEPER_PASSWORD=` · `deploy/runpod/entrypoint.sh` يضيفها لقائمة المتغيّرات الإلزاميّة (‏RunPod حاويةٌ واحدة تُهيّئ العنقود بنفس السكربت). حارس انجرافٍ `tests/unit/test_role_provisioning_wiring.py` يقارن الأدوار الثلاثة (`app_rw`/`outbox_relay`/`retention_sweeper`) عبر هذه المصادر الأربعة (‏`provision.py`، `10-roles.sh`، `docker-compose.yml`، `.env.example`) فيمسك أيّ دورٍ يُضاف إلى `_require_roles` بلا تهيئةٍ مطابقة. **ما لم يُوصَل عمداً**: لا `RETENTION_DATABASE_URL` في `entrypoint.sh` (خلافاً لـ`RELAY_DATABASE_URL`) — لا خدمةً دائمةً تستهلكها؛ العملية اليدويّة تبني DSN‑ها بنفسها وقت الاستدعاء (أسفل).

```bash
# استدعاءٌ يدويّ عبر Compose — لاحظ استبدال DATABASE_URL بدور retention_sweeper
# (المتغيّر PGBOUNCER_URL أدناه هو نفس عنوان app/outbox-relay: pgbouncer:6432)
docker compose exec -e DATABASE_URL="postgresql+asyncpg://retention_sweeper:${RETENTION_SWEEPER_PASSWORD}@pgbouncer:6432/${POSTGRES_DB:-aizzak}" \
    app python -m app.ops.retention sweep --dry-run
```

> **لا جدولة آليّة بعد.** هذه الخطوة أداةٌ يدويّةٌ فقط (‏`python -m app.ops.*` كما في §4.2) — لا `cron` ولا مهمّةً دوريّةً تُشغّلها تلقائيّاً؛ التشغيل الدوريّ الفعليّ قرارٌ تشغيليٌّ منفصل (مثلاً: `cron` شهريّ على المضيف يستدعي `sweep` بلا `--dry-run`).

### 4.4 مقياسا الـ Outbox والـ DLQ — `GET /metrics` (‏P1‑3 · `p1-hardening-plan.md` §3 خطوة 10)

07‑nfr‑slo §7 يسمّي زمن دورة الـOutbox وامتلاء DLQ «مؤشّرَي صحّةٍ رئيسيّين» — حتّى هذه الخطوة لا شيء يقيسهما. `GET /metrics` (بصيغة Prometheus) يعرض **مقياسَي الخطوة 10**، ومنذ ن‑10 **مقياساً ثالثاً** من نوعٍ مختلف (سبرُ حياةِ تبعيّةٍ لا حالةَ منصّة — تفصيله في §3.1 أعلاه، لا هنا):

```
aizzak_outbox_oldest_unpublished_age_seconds        # كم ثانيةً مكث أقدم صفٍّ غير منشور (0 إن لم ينتظر شيء)
aizzak_dlq_depth{stream="stream.files"}              # XLEN لكلّ stream.<وحدة>.dlq — لكلّ مجرًى في الطوبولوجيا الثابتة
aizzak_dlq_depth{stream="stream.knowledge"}
aizzak_dlq_depth{stream="stream.media"}
aizzak_dlq_depth{stream="stream.memory"}
aizzak_vault_authenticated                           # 1 إن كانت هذه العمليّة تستطيع نداء Vault مُصرَّحاً به الآن، 0 خلا ذلك (ن‑10)
```

> ⚠️ **وقائمةُ المجاري هذه كانت مكتوبةً بيدٍ وناقصة حتّى 2026‑08‑15** (`("stream.knowledge", "stream.media")`) — بينما المدخلة الوحيدة على المكدّس الحيّ كانت على **`stream.memory.dlq`**، أي أنّ المقياس كان سيُبلِّغ صفراً نظيفاً عن كلّ ما يعرفه بينما الطابور الذي فيه شيءٌ **لا يُقرأ أصلاً**. لم يكشفه شيءٌ لأنّ إنذاره لا كاشطَ يُقيّمه بعد. صار مُشتقّاً من `framework/events/topology.py` وحُرِس باختبار ([§3.138](../log/3.138.md) · ت‑6).

```bash
docker compose exec app curl -s http://127.0.0.1:8000/metrics   # من داخل الشبكة فقط — انظر التحذير أدناه
```

> ⭐ **مزلق تعدّد العمليّات، وكيف عُولج.** `app` يعمل بعدّة عمّال gunicorn (‏`WEB_CONCURRENCY=2` افتراضيّاً، `Dockerfile`/`docker-compose.yml`/`deploy/runpod/supervisord.conf`)، فتسجيل Prometheus الافتراضيّ (سجلٌّ داخل ذاكرة عمليّةٍ واحدة) كان سيُرجع رقماً يتذبذب بلا معنًى حسب أيّ عمليّةٍ استقبلت الكشطة — نفس جذر P0‑2 (‏`ConnectionHub` داخل العمليّة، §3.81). **الحلّ المُطبَّق: لا حالة عمليّة إطلاقاً.** كلّ كشطةٍ تبني `CollectorRegistry` جديدةً وتقرأ Postgres (‏`SELECT min(created_at) ... WHERE published_at IS NULL`، عبر الفهرس الجزئيّ `ix_outbox_unpublished`) وRedis (‏`XLEN`) **مباشرةً** لحظة الطلب (`src/app/api/metrics.py`/`src/app/infrastructure/monitoring/metrics_source.py`) — فأيّ عمليّتَي gunicorn تُعيدان **نفس الرقم** لأنّه ليس ذاكرةً خاصّةً بأيٍّ منهما، بل قراءةً حيّةً من مصدرٍ خارجيٍّ مشترك. مُثبَتٌ حيّاً (‏`tests/integration/test_metrics_source_live.py::test_two_independent_instances_report_the_identical_value`): محرّكان ومُتّصلا Redis منفصلان كلّياً (تماماً كما ستحمل كلّ عمليّة gunicorn شقيقة اتّصالاتها الخاصّة) يقرآن نفس الحالة الحقيقيّة ويتّفقان.

> ⭐ **دورٌ خامسٌ لقاعدة البيانات: `metrics_reader`.** `app_rw` يملك `INSERT` فقط على `platform.outbox` (‏`provision.py`)، فلا يستطيع الإجابة عن عمر أقدم صفٍّ إطلاقاً. بدل توسيع منحة `app_rw` (يهدم ضمانها المُعلَن)، دورٌ خامسٌ منفصل — نظير `outbox_relay`/`retention_sweeper` — بمنحة `SELECT` وحيدة على `platform.outbox` (‏`METRICS_GRANTS`)، موصولٌ عبر `METRICS_DATABASE_URL` (اتّصالٌ ثانٍ داخل عمليّة `app` نفسها، منفصلٌ عن `DATABASE_URL`/`app_rw`). لا هجرة RLS مطلوبة (‏`platform.outbox` بلا سياسة RLS أصلاً، خلافاً لـ`idempotency_keys`).

> ⛔ **`/metrics` محجوبةٌ عمداً عبر nginx** — `deploy/nginx/app-locations.conf`/`deploy/runpod/nginx.conf` يجيبان عليها بـ404 محليّاً **قبل** `location /`، فلا تُنشَر إلى الإنترنت أبداً (نفس حدّ ثقة `embedding` — `expose` لا `ports`). كاشطٌ حقيقيّ يصل المنفذ الداخليّ (‏`app:8000/metrics`) مباشرةً عبر شبكة Compose، لا عبر nginx.

> **الإنذارات الثلاثة** (‏`deploy/prometheus/alerts.yml` — أداةٌ لكاشطٍ لاحق، لا خدمة Prometheus قائمة اليوم عمداً):
> - **زمن دورة Outbox > 3ث لمدّة 2 دقيقة** — 3ث هو ميزانيّة p99 نفسها في `07-nfr-slo.md` §2؛ دقيقتان تستبعد وميضاً عابراً (‏240 ضِعف فترة الاستطلاع الافتراضيّة 500ms) وتُمسك عطلاً حقيقيّاً بسرعة.
> - **عمق DLQ > 0 لمدّة 5 دقائق** — لا عمق «طبيعيّاً» غير صفريّ لهذا الطابور؛ الوصول إليه أصلاً استثناءٌ (‏5 محاولاتٍ فاشلة أو مظروفٌ مشوَّه). **الاستجابة المرجعيّة مكتوبةٌ في الإنذار نفسه**: `python -m app.ops.dlq peek/requeue/purge` (‏P1‑4، §4.2 أعلاه).
> - **`aizzak_vault_authenticated < 1` لمدّة 5 دقائق — `critical` لا `warning`** (ن‑10). الفارق مقصود: الإنذاران أعلاه يصفان **تراكم عمل**، وهذا يصف **قدرةً مفقودة سلفاً**. و`for: 5m` هنا كتمُ ضجيجٍ لا مهلةُ تعافٍ — الحالة لا تُشفى ذاتيّاً، لأنّ إعادة تسجيل الدخول تستعمل **نفس** `VAULT_SECRET_ID` الذي أُقلعت به العمليّة. **الاستجابة مكتوبةٌ في الإنذار نفسه، وترتيبها مُلزِم**: أوقف الكاشط مع `app` → افكّ القفل → اسكك → `up -d --force-recreate --no-deps` (§3.1 أعلاه).

```bash
curl -s  http://localhost/health          # liveness
curl -sk https://localhost/health/ready   # readiness عبر TLS (الشهادة موقَّعةٌ ذاتيّاً ⇒ -k)
docker compose ps                          # حالة كلّ خدمة
```

> ⚠️ **فحص الحافّة إلزاميّ، وهذا هو الدرس الأغلى في المرحلة 7.** كلّ فحصٍ آخر في `docker-compose.yml` يسبر خدمةً **من داخل نفسها** (فحص `app` يستدعي `127.0.0.1:8000` في حاويته). ولهذا كانت علّة #10 خفيّة إلى هذا الحدّ: nginx يوجّه إلى عنوانٍ ميّت ويجيب **502** للعالم، بينما `docker compose ps` يقول إنّ كلّ شيءٍ `healthy` وسجلّ التطبيق مليءٌ بـ`200` — **ولا مؤشّر واحد يربط الطرفين**.
>
> فحص خدمة `nginx` يعبر ذلك الرابط: يخرج من مستمع nginx، يمرّ بإعداد الوكيل، يبلغ التطبيق ويعود — على **المخطّطين معاً** (`http` و`https`، فلـ443 شهادتُه وإعدادُه اللذان لا يشهد لهما 80). **مُثبَتٌ بالنقيض**: إيقاف `app` بلا لمس nginx ⇒ الحافّة **504** والخدمة تصير `unhealthy`؛ إعادته ⇒ `healthy` و200.

> `/health/ready` **لا يلمس أيّ تبعيّة** عمداً (`health.py`: الجاهزيّة «انتهى الإقلاع» لا «التبعيّات حيّة») — فحاويةٌ صحّية ليست بنفسها دليلاً على مسار البيانات. لذلك توجد إثباتات `deploy/smoke/`.

### 4.5 مسار تدوير مفتاح Transit — `python -m app.ops.rotate_transit` (‏P1‑9 · `p1-hardening-plan.md` §3 خطوة 12)

`transit/rewrap/tenant-secrets` كان **غير ممنوحٍ عمداً** في `deploy/vault/app-policy.hcl` منذ 7.3 (‏§3.76): «امتيازٌ لا يمارسه أحدٌ امتيازٌ مجّانيّ… يخصّ الخطوة التي تنفّذ التدوير، ويُضاف مع أوّل مستدعٍ له». هذه الخطوة هي ذلك المستدعي: المنحة أُضيفت **مع** `app.ops.rotate_transit`، لا قبله.

> ⚠️ **الدرس الأهمّ في هذه الخطوة: تدوير المفتاح وحده لا يغيّر شيئاً في النصوص المعمّاة القديمة.** Vault Transit يحتفظ بكلّ نسخ المفتاح القديمة ويفكّ بها تلقائيّاً؛ نصٌّ مُعمًّى بالنسخة `1` **يُقرأ بنجاح** بعد تدوير المفتاح إلى النسخة `2` بلا أيّ `rewrap`. هذا **لا يثبت شيئاً عن نجاح التدوير** — إنّما يثبت أنّ Vault لم يُتلف شيئاً بعد. القرار الفعليّ («الآن هذا الصفّ مُعمًّى بالنسخة الحاليّة») لا يصبح حقيقةً إلّا حين تُعاد كتابة النصّ في قاعدة البيانات، وهو بالضبط ما تفعله هذه الأداة ولا شيء غيرها.

**التسلسل الكامل — ثلاث خطواتٍ، كلّ واحدةٍ بصلاحيّةٍ مختلفة:**

```bash
# 1) المشغّل يدور المفتاح (صلاحيّة إدارة مفاتيح — توكن جذرٍ، ليست AppRole التطبيق):
docker compose exec vault vault write -f transit/keys/tenant-secrets/rotate

# 2) الأداة تُعيد التعمية وتُخزّن — dry-run أوّلاً لرؤية العدد قبل الالتزام:
docker compose exec -e DATABASE_URL="postgresql+asyncpg://transit_rotator:${TRANSIT_ROTATOR_PASSWORD}@pgbouncer:6432/${POSTGRES_DB:-aizzak}" \
    app python -m app.ops.rotate_transit sweep --dry-run
docker compose exec -e DATABASE_URL="postgresql+asyncpg://transit_rotator:${TRANSIT_ROTATOR_PASSWORD}@pgbouncer:6432/${POSTGRES_DB:-aizzak}" \
    app python -m app.ops.rotate_transit sweep

# 3) المشغّل يرفع min_decryption_version -- لا رجعة، ونفّذها فقط بعد التحقّق
#    من (2) أعلاه:
docker compose exec vault vault write transit/keys/tenant-secrets/config min_decryption_version=<الرقم الجديد>
```

**لماذا هذا الترتيب لا غيره.** الخطوة (1) صلاحيّة **إدارة** مفتاح (`transit/keys/tenant-secrets/rotate`) — توكنٌ جذريٌّ أو مسؤول Vault، **لم** ولن تُمنح لسياسة `app` (‏`app-policy.hcl` يسمّي هذا صراحةً في قسم «‏Deliberately NOT granted» ويُثبته `approle_smoke.py` رفضاً فعليّاً، أسفل). الخطوة (2) هي الوحيدة التي تحتاج المنحة الجديدة (`transit/rewrap/tenant-secrets`، صلاحيّة **استخدام** لا إدارة) وتعمل بدور قاعدة البيانات الخامس `transit_rotator` (‏`SELECT` + `UPDATE` مقصورٌ على عمود التعمية وحده على الجداول الثلاثة — لا `app_rw` ولا أيّ دورٍ آخر يوسَّع). الخطوة (3) **لا رجعة عنها إطلاقاً**: أيّ نصٍّ لم تُعِد الخطوة (2) تعميته يفشل فكّه بعدها بلا استثناء — ولهذا تسبقها (2) دائماً ولا تُنفَّذ (3) إلّا بعد التحقّق من عدد الصفوف المُعاد تعميتها (‏`scanned`/`rewrapped` في مخرَج الأداة) ومطابقتهما لما تتوقّعه.

**الأداة نفسها آمنةٌ لإعادة التشغيل، ومُصمَّمةٌ لتُقاطَع في أيّ لحظة.** كلّ صفٍّ يُقرأ ويُعاد تعميته ويُكتَب في معاملةٍ قصيرةٍ خاصّةٍ به — لا معاملة واحدة للجدول كلّه (خلافاً لـ`app.ops.retention`: هناك جملة SQL واحدة بلا استدعاء شبكةٍ بينيّ، وهنا كلّ صفٍّ يستدعي Vault فعليّاً فحجز معاملةٍ طويلة أثناء ذلك يحجز اتّصالاً وأقفالاً بلا فائدة). فإن قُتلت العمليّة في المنتصف: كلّ صفٍّ التزم يبقى بالنسخة الجديدة، وكلّ صفٍّ لم يُلتَزَم بعد يُعاد التقاطه ببساطةٍ عند التشغيل التالي (إعادة تعميته عبر Vault فعلٌ رخيصٌ بلا أثر جانبيّ). ⚠️ **الفخّ الذي كان سيكسر هذا الضمان، ومُصحَّحٌ قبل الشحن**: الافتراض البديهيّ «رفض Vault ‏rewrap لنفس النصّ مرّتين يعيد نفس البايتات» **خاطئٌ، وقيسَ حيّاً**: Vault يولّد nonce عشوائيّاً في كلّ نداء `rewrap` بصرف النظر عن تغيّر نسخة المفتاح من عدمه، فمقارنة البايتات كانت ستُعيد تعمية كلّ صفٍّ في كلّ تشغيلٍ للأبد. المقارنة الصحيحة على **رقم نسخة المفتاح** المُضمَّن في بادئة Vault نفسها (`vault:v<n>:...`)، لا على محتوى النصّ.

**التحقّق الحيّ الوحيد الذي يُثبت شيئاً حقيقيّاً** (‏`tests/integration/test_vault_secrets.py`): تعمية بالنسخة 1 ← تدوير المفتاح إلى 2 ← إعادة تعمية **أحد** نصّين فقط ← رفع `min_decryption_version` إلى 2 ← النصّ **غير المُعاد تعميته** يفشل فكّه الآن، والنصّ **المُعاد تعميته** يبقى يفكّ إلى نفس البايتات الأصليّة تماماً — على مفتاحٍ اختباريٍّ فريدٍ يُحذف بعد الاختبار، لا على `tenant-secrets` المشترك أبداً. ادّعاء الخطة الأصليّ («نصٌّ بالنسخة 1 يُقرأ بعد التدوير إلى 2») لا يُثبت شيئاً بمفرده — Vault يفكّ نصوص كلّ النسخ القديمة تلقائيّاً حتّى بلا `rewrap` على الإطلاق؛ التسلسل أعلاه هو الوحيد الذي يجعل `rewrap` حاسماً فعلاً.

**السياسة مُثبَتةٌ في الاتّجاهين تحت توكن AppRole حقيقيّ** (‏`deploy/smoke/approle_smoke.py`، منهج §3.76): ‏[3b] يثبت أنّ `rewrap` يعمل ويعيد نصّاً لا يزال يفكّ إلى نفس القيمة، و[7] يثبت أنّ `transit/keys/tenant-secrets/rotate` (إدارة المفتاح) **مرفوضٌ فعلاً** تحت نفس التوكن — أي أنّ توكن التطبيق يستطيع **استخدام** أيّ نسخةٍ يختارها مشغّلٌ بشريّ، ولا يستطيع أبداً أن يُقرّر بنفسه أنّ نسخةً جديدة يجب أن تُصنَع.

`DATABASE_URL` لهذه العمليّة يجب أن يكون DSN الخاصّ بـ`transit_rotator` — نفس اصطلاح كلّ عمليّةٍ بدورها الخاصّ (`aizzak_owner` يهاجر، `app_rw` يُنتِج، `outbox_relay` ينشر، `retention_sweeper` يكنس، `transit_rotator` يُعيد التعمية؛ لا دورٌ يرتدي قبّعة دورٍ آخر). **لا جدولة آليّة** (نفس §4.3 — أداةٌ يدويّةٌ تُشغَّل حين يقرّر مشغّلٌ التدوير فعليّاً، لا مهمّةٌ دوريّة).

### 4.6 أداة تطهير محتوى مساحة العمل — `python -m app.ops.purge` (BE-ADM-014)

`SqlPlatformAccountManager.delete` (BE-ADM-006) يُشيِّد **شاهدَ قبرٍ**: يُبدِّل حالة المستخدم إلى
`deleted` ويمحو هويّته (`email`/`display_name`)، لكنّه **لا يمسّ** محتوى مساحة عمله إطلاقاً —
لا محادثاتها، لا ملفّاتها، لا وثائقها المفهرَسة، لا متّجهات Qdrant، لا كائنات MinIO. هذه الأداة هي
الاكتساح الدوريّ الذي يطهِّر ذلك المحتوى بعد **نافذة احتفاظٍ** (30 يومًا افتراضيّاً،
`app.ops.purge.PURGE_RETENTION`) — نافذةٌ للمُشغِّل لا للمستخدم المحذوف: مهلةٌ كافيةٌ لملاحظة خطأٍ
واستعادته من نسخةٍ احتياطيّة، قصيرةٌ بما يكفي ليبقى «المحذوف» يعني شيئاً. ⚠️ **REVIEW POINT** مكرَّرٌ
هنا كما في نصّ الأداة نفسه: إن نصّت سياسة خصوصيّة/DPA على أجلٍ مختلف، فذلك الأجل هو ما يُعتمَد.

**ما تفعله بالضبط**: لكلّ مساحة عملٍ **لا يوجد فيها أيّ مستخدمٍ غير محذوف** وتجاوز أحدث شاهدَ قبرٍ
فيها نافذة الاحتفاظ — تُسقِط مجموعتَي Qdrant (`kn-<ws>` ثمّ `mem-<ws>`)، ثمّ تحذف كلّ كائنات MinIO
تحت البادئة `<ws>/`، ثمّ تحذف صفوف عشر وحدات (Postgres، مُعاملةٌ واحدة لكلّ (مساحة عمل، مخطّط))، ثمّ
تُنهي بمعاملةٍ أخيرةٍ تجعل `workspace.workspaces.status='archived'`/`purged_at=now()` وتُلحق صفّ
تدقيقٍ `workspace.purged` في `platform.admin_audit_log`. **لا يُحذف صفّ `workspace.workspaces`/
`workspace.users` نفسه إطلاقاً** — يبقى شاهدُ القبر شاهدًا، ويبقى `platform.admin_audit_log` قادرًا
على الإشارة إليه.

**قبل أيّ تشغيلٍ فعليّ**: تأكّد من وجود نسخةٍ احتياطيّةٍ/PITR سارية لقاعدة البيانات — هذا تطهيرٌ
لا رجعة فيه، ولا "تراجع" هنا كما لا "تراجع" في تدوير مفتاح Transit (§4.5). التسلسل الموصى به دائمًا:

```bash
# 1) استطلاعٌ للقراءة فقط — Postgres وحده، لا Qdrant ولا MinIO:
docker compose exec -e DATABASE_URL="postgresql+asyncpg://workspace_purger:${WORKSPACE_PURGER_PASSWORD}@pgbouncer:6432/${POSTGRES_DB:-aizzak}" \
    app python -m app.ops.purge scan

# 2) معاينةٌ كاملة (Qdrant/MinIO/Postgres معًا) بلا أيّ كتابة:
docker compose exec -e DATABASE_URL="postgresql+asyncpg://workspace_purger:${WORKSPACE_PURGER_PASSWORD}@pgbouncer:6432/${POSTGRES_DB:-aizzak}" \
    app python -m app.ops.purge run --dry-run

# 3) التشغيل الفعليّ -- يرفض بلا `--yes` صراحةً (نفس اصطلاح `app.ops.dlq purge`):
docker compose exec -e DATABASE_URL="postgresql+asyncpg://workspace_purger:${WORKSPACE_PURGER_PASSWORD}@pgbouncer:6432/${POSTGRES_DB:-aizzak}" \
    app python -m app.ops.purge run --yes
```

**الدور السابع لقاعدة البيانات: `workspace_purger`.** خلافاً لـ`retention_sweeper` (الذي يحمل سياسة
`USING (true)` عابرة المستأجرين على الجداول التي يكنسها)، هذا الدور **لا** يحمل مثل هذه السياسة على
أيّ جدولٍ مستأجَرٍ يحذف منه — يضبط `app.workspace_id` GUC لمساحة عملٍ واحدةٍ في كلّ مرّة (نفس اصطلاح
`app_rw` تمامًا) ويعتمد على سياسة `tenant_isolation` العاديّة، فإسقاط `set_config` سهوًا يفشل بأمانٍ
إلى صفر صفٍّ متأثّرٍ لا إلى كلّ المستأجرين. الاستثناء الوحيد هو سياسةٌ SELECT-only عابرة المستأجرين
على `workspace.users` وحده (‏`workspace_purger_select`، `migrations/versions/workspace/
0009_workspace_purge.py`) تتيح لـ`find_candidates` مسح كلّ مساحات العمل بحثًا عن مرشّحاتٍ مؤهّلة —
ومنحته على هذا الجدول مقصورةٌ على أعمدة الحالة (`id, workspace_id, status, deleted_at`)، **لا**
`email`/`display_name`/`firebase_uid` إطلاقاً؛ ولا `UPDATE`/`DELETE` على `users` بتاتًا — يبقى شاهد
القبر ملكًا لـ`SqlPlatformAccountManager.delete` وحده. `DATABASE_URL` لهذه العمليّة يجب أن يكون DSN
الخاصّ بـ`workspace_purger` — نفس اصطلاح كلّ عمليّةٍ بدورها الخاصّ. **لا جدولة آليّة** (نفس §4.3/§4.5
— أداةٌ يدويّةٌ، والتشغيل الدوريّ الفعليّ قرارٌ تشغيليٌّ منفصل، مثلاً `cron` شهريّ يستدعي `run --yes`).

### 4.7 فهارس بطاقة Qdrant للصناديق القائمة — `python -m app.ops.payload_indexes` (خطّة الوحدات §5‑ب · الخطوة ١٦)

`ensure_hybrid_collection` تفهرس `workspace_id`/`document_id`/`space` **فور إنشاء** الصندوق، وتخرج
مبكّرًا إن كان الصندوق موجودًا — فكلّ صندوق `kn-<workspace_id>` أُنشئ قبل تلك الشيفرة يحمل **صفر
فهارس بطاقة** ولا مسار كتابةٍ سيمنحه واحدًا أبدًا. (وقبل خطوة الوحدات ٩ لم يكن في المشروع كلّه فهرسُ
بطاقةٍ واحد: `create_payload_index` لم تُستدعَ قطّ.) هذه الأداة هي المرّة الواحدة التي تسدّ ذلك.

**ما تفعله بالضبط**: تسأل Qdrant عن صناديقه، تختار ما يبدأ بـ`kn-` وحده، وتُنشئ لكلٍّ منها ما ينقصه
من المفاتيح الثلاثة (‏`space` بـ`is_tenant=True`، والآخران عاديّان)، ثمّ **تقرأ المخطّط من الخادم
ثانيةً** وتُبلِّغ بما يحمله فعلًا لا بما نجحت مناداته. تخرج بـ`1` إن بقي صندوقٌ ناقصًا.

**آمنةٌ وقابلةٌ لإعادة التشغيل**: إنشاء فهرس لا يضيف بيانًا ولا يحذف بيانًا ولا يعيد كتابة حمولة —
ولذلك **لا `--yes`** هنا خلافًا لـ`app.ops.purge`/`app.ops.dlq purge`. وإعادة التأكيد عديمة الأثر
(‏مُقيسةٌ حيًّا: النداء يعود `completed`، وإعادةُ تأكيدٍ بـ`is_tenant` مختلف **تستبدل** الفهرس بلا
تعارض) — فالعطبُ في المنتصف يُعالَج بإعادة التشغيل، لا بتقريرٍ ينتهي بـ«نجح معظمه».

```bash
# 1) معاينة: ما الذي سيُفهرَس، بلا أيّ كتابة
docker compose exec app python -m app.ops.payload_indexes run --dry-run

# 2) التشغيل الفعليّ على كلّ صناديق `kn-`
docker compose exec app python -m app.ops.payload_indexes run

# 3) أو صندوقٌ واحد بالاسم
docker compose exec app python -m app.ops.payload_indexes run --collection kn-<workspace_id>
```

**لا قاعدة بيانات ولا دور** — خلافًا لكلّ `app.ops.*` أعلاه: الأداة لا تفتح `DATABASE_URL` أصلًا،
لأنّ السؤال «أيّ الصناديق موجود» لا يُجيب عنه إلّا Qdrant نفسه، و`QDRANT_URL` مضبوطٌ في حاوية `app`
سلفًا.

> 📌 **صناديق `mem-` خارج النطاق قصدًا**: هي تُهيَّأ عبر عقد `VectorStore` الأضيق الذي لا يطلب فهرسًا
> ولا تحمل نقاطُه مفتاح `space` أصلًا (خطّة الوحدات §3.4) — و`--collection` **يضيّق** المجموعة
> المُكتشَفة ولا يوسّعها، فاسمٌ خارجها يُرفض بدل أن يُنفَّذ.
>
> ⚠️ **والفهرسة ليست إعادةَ فهرسة**: النقاط المكتوبة قبل خطوة الوحدات ٨ لا تحمل مفتاح `space` في
> حمولتها، وفهرسها لا يخلقه — بحثٌ مقيَّدٌ بوحدةٍ لا يطابقها بلا خطأ. علاجُ ذلك
> `POST /api/v1/knowledge/reindex` (خطّة الوحدات §5‑أ)، وهو عملٌ آخر.

## 5) فحص الصحّة — من يُعلن حياته، وبأيّ دليل ([§3.136](../log/3.136.md) · ت‑3)

`docker compose ps` صار يقول شيئاً عن **كلّ** خدمةٍ طويلة. حتّى 2026‑08‑13 كانت **ستٌّ من ثلاث عشرة بلا فحصٍ إطلاقاً** (`qdrant` · `pgbouncer` · `ollama-bridge` · `outbox-relay` · العاملان، ثمّ الثلاثة بعد [§3.134](../log/3.134.md))، ولذلك نتيجتان ملموستان: `depends_on` لم يكن يملك لـ`qdrant`/`pgbouncer` أقوى من `service_started` — **والبدء ليس الجاهزيّة** — وعاملٌ توقّفت حلقته كان **غير مرئيٍّ تماماً**.

| الخدمة | ماذا يقيس الفحص فعلاً |
|---|---|
| `pgbouncer` | **يعبر الوصلة**: `psql ... -c 'select 1'` عبر المُجمِّع نفسه ⇒ اتّصالُ خادمٍ حقيقيٌّ إلى Postgres. (‏`pg_isready -p 6432` جُرِّب ورُفض: يقول «يقبل الاتّصالات» بمجرّد أن يستمع المُجمِّع — أي لا يزيد شيئاً على `service_started` الذي يحلّ محلّه.) الاعتماد هو `DB_USER`/`DB_PASSWORD` **من بيئة الحاوية نفسها** بـ`$$`، فلا يدخل شيءٌ حسّاسٌ في مخرجات `docker compose config` |
| `qdrant` | `/readyz` (لا `/livez`: الأوّل «كلّ الشظايا تخدم»، والثاني «العمليّة حيّة») — عبر `/dev/tcp` في **bash صراحةً**، لأنّ الصورة لا تحمل `curl` ولا `wget`، و`CMD-SHELL` كان سيشغّل `sh` الذي لا يعرف `/dev/tcp` |
| `ollama-bridge` | **من طرفٍ إلى طرف**: `wget` يدخل الجسر على 11435 ويخرج من Ollama الأصليّ على 11434. socat مستمعٌ وهدفه ميّت لا يمرّر شيئاً |
| `worker-memory` · `worker-knowledge` · `worker-media` · `outbox-relay` | **نبضٌ**، لأنّها لا تستمع على منفذٍ أصلاً — انظر أدناه |

> 📌 **ولا شيء يعتمد على صحّة `ollama-bridge`، عمداً.** Ollama وحدةٌ أصليّةٌ في WSL خارج دورة حياة Compose؛ ربطُ إقلاع المكدّس بها يستبدل تدهوراً مرئيّاً بآخر خفيّ. «غير صحّي» هنا معناه «نداءات LLM ستفشل»، معروضاً في `docker compose ps` بدل أن يظهر في خطأ طلبٍ فقط.
>
> ✅ **وأُغلقت معها حافّةٌ مُعلَنةٌ منذ [§3.133](../log/3.133.md)**: `app` صارت تُعلن `qdrant` في `depends_on` (‏`service_healthy`) — عين عطب [§3.111](../log/3.111.md): `QDRANT_URL` تسمّي `qdrant:6333` من الطور الأوّل، والحافّة غير مُعلَنة ⇒ `docker compose up -d app` وحده كان يقلعها بلا مخزن المتّجهات. وحوافّ `pgbouncer`/`qdrant` كلّها صارت `service_healthy` بدل `service_started`.

### 5.0 نبضُ العمليّات بلا منفذ

العمّال الثلاثة والمُرحّل حلقاتٌ حاجبةٌ لا تستمع على شيء، فلا نقطةَ نهايةٍ تُستدعى. كلٌّ منها **يختم ملفاً** مرّةً في كلّ دورةٍ مكتملة، والفحص يقرأ عمر الختم:

```bash
docker compose exec worker-memory python -m app.ops.healthcheck memory   # 0 حيّ · 1 بائت · 2 سوء إعداد
docker compose exec worker-memory ls -l --time-style=+%H:%M:%S /tmp/aizzak-heartbeat/
```

* **الأسماء أربعة**: `memory` · `knowledge` · `media` · `outbox-relay` — اسمٌ خاطئ يخرج بـ**2** ويسرد الصحيح، فلا يُقرأ خطأٌ مطبعيٌّ في Compose كعاملٍ ميّت.
* **ملفٌّ لكلّ عمليّة، لا لكلّ حاوية**: RunPod يشغّل `worker` و`outbox-relay` في حاويةٍ واحدة، ومسارٌ مشتركٌ كان سيسمح لعمليّةٍ ميّتةٍ أن تركب نبضَ شقيقتها الحيّة — وهو بالضبط ما فعلته اليتيمة في ت‑7.
* **المُرحّل ينبض على الدورة النظيفة وحدها**: مُرحّلٌ عاجزٌ عن بلوغ Postgres يظلّ يدور ويضاعف تراجعه ويبقى `Up` إلى الأبد — والامتناع عن النبض في مسار الفشل هو ما يحوّل ذلك إلى حاويةٍ غير صحّيّة.
* **`HEARTBEAT_MAX_AGE_S` تسامحٌ لا إيقاع**: العامل ينبض كلّ `CONSUMER_BLOCK_MS` (‏5 ث) وهو خامل، لكنّ النبضة **لا تقع أثناء معالجٍ يعمل**، وقد يعمل معالجٌ مشروعٌ دقائق. الافتراضيّ **300 ث** و`worker-media` وحده **600** (توليد الصور، `Limits.media_timeout_s = 300`). عتبةٌ أضيق كانت ستُبلّغ عن عاملٍ منشغلٍ بعمله كأنّه ميّت، فيتعلّم المشغّل تجاهل العمود — وهي عين آفة ت‑6.
* **`HEARTBEAT_DIR=` فارغاً يعطّل النبض** (المسار الصحيح لتشغيلٍ من صدفةٍ بلا Docker)، والفاحص حينها يخرج بـ**2** لا بـ**0**: فحصٌ لا يستطيع أن يفحص شيئاً لا يُبلّغ صحّةً.

### 5.1 الإثباتات الحيّة (`deploy/smoke/`)
```bash

python3 deploy/smoke/ws_smoke.py localhost 443 --tls   # wss:// — نفس الفحوص فوق TLS
docker compose exec app python /app/deploy/smoke/stack_smoke.py     # OPS-02 · RLS · توقيع مسبق
docker compose exec -e VAULT_SECRET_ID=<id> app python .../approle_smoke.py   # AppRole + منعُ ما لا يُمنَح
```

## 7) البذر والتحقّق اليدوي
1. احصل على Firebase ID Token (مشروع اختباري) وضعه في `Authorization: Bearer`.
2. أول طلب مُصادَق ⇒ بذر المستخدم JIT + Workspace + دور `owner`.
3. جرّب التدفّق الكامل:
   ```
   POST /api/v1/files            → upload_url ثم ارفع إلى MinIO ثم POST /files/{id}/complete
   (حدث files.file.uploaded.v1 → knowledge_worker يفهرس → knowledge.document.indexed.v1)
   POST /api/v1/agents/rag_agent/invoke  (Accept: text/event-stream)  → بثّ الردّ
   POST /api/v1/media/jobs        → 202 ثم GET /media/jobs/{id} حتى succeeded
   POST /api/v1/integrations/connections → authorize_url ثم callback (السرّ مُعمّى عبر Transit) → GET /integrations/tools
   GET  /api/v1/usage             → ملخّص الاستهلاك (يُلتقَط عبر منفذ المُنسِّق، لا Streams)
   ```

## 8) استكشاف الأعطال
| العرض | الفحص |
|-------|-------|
| **`app` في حلقة إعادة تشغيل بـ`secret does not exist in Vault`** | Vault دائمٌ الآن (§3.4) فهذا لم يعد سببه فقدان الذاكرة عادةً — تحقّق من `docker compose ps vault-bootstrap` وسجلّه |
| **`vault-start: ⛔ 'operator init' failed, and .../init.json does not exist`** | حجم `vault-data` مُهيَّأٌ من قبل لكنّ `vault-init` مفقودٌ أو استُبدل — استعادة `init.json` من نسخةٍ احتياطيّة هي السبيل الوحيد (§3.4) |
| **الحافّة 502/504 بينما `ps` يقول `healthy`** | كان عَرَض علّة #10؛ اليوم يُظهره فحص حافّة `nginx` مباشرةً. راجع `docker compose ps` لخدمة `nginx` نفسها |
| **AppRole لا يُستعمل رغم ضبط `ROLE_ID`/`SECRET_ID`** | `VAULT_TOKEN` غير فارغ — التوكن يفوز دائماً (§3.1) |
| **Vault يعمل ساعةً ثمّ يفشل كلّ سرّ** | انتهاء `token_ttl` (توكن AppRole للتطبيق) بلا إعادة مصادقة (§3.1). تحقّق أنّ `relogin` موصولٌ في جذر التركيب |
| **`role_id` غير صالح** | الدور أُنشئ بمعرّفٍ عشوائيّ لأنّ `AIZZAK_APPROLE_ROLE_ID` لم يكن مضبوطاً وقت أوّل إقلاع؛ ثبّته في `.env` وأعد تشغيل `vault-bootstrap` |
| **مكدّسٌ قديم ⇒ `400 invalid role or secret ID` فجأة** | انقضاء `secret_id` (§3.1 ن‑10) لا اعتمادٌ خاطئ — اسكك `secret_id` جديداً (§3.1 خطوة 2) وأعد **إنشاء** `app` |
| **`403 permission denied` بأخطاءٍ فارغة، وسرٌّ جديدٌ صحيحٌ لا يُقبَل** | **قفل مستخدم Vault** تسبّبت به حلقة انهيار `app` (§3.1، §3.94). `docker compose stop app` أوّلاً، ثمّ `sys/locked-users/<accessor>/unlock/<role_id>`، ثمّ اسكك وأعد الإنشاء |
| **`aizzak_vault_authenticated 0` (أو إنذار `AizzakVaultAuthFailing`) بينما `docker compose ps` يقول `healthy`** | هذا **بالضبط** ما أُضيف المقياس ليكشفه (ن‑10، §3.1): اعتماد Vault ميّت والفحص لا يلمس Vault. ⚠️ **أوقف الكاشط مع `app`** قبل أيّ شيء — كلّ كشطةٍ محاولةُ دخولٍ فاشلة تُعيد إشعال قفل المستخدم — ثمّ افكّ القفل، ثمّ اسكك `secret_id`، ثمّ `up -d --force-recreate --no-deps app`. غياب المقياس من الردّ رأساً معناه مختلف: `vault_health` غير موصولٍ في `create_production_app` |
| **تدويرُ كلمة مرورٍ «يعود» بعد حين** | `docker compose start` أقلع `vault-bootstrap` القديم فأعاد بذر `secret/db` بالسرّ البائت — استعمل `up -d --force-recreate --no-deps` لا `start` |
| **`app` لا يُقلع إطلاقاً (لا `/health` أبداً)، لا مجرّد فشل سرٍّ لاحق** | Redis غير متاحٍ لحظة الإقلاع (§3.1‑ب ن‑1 — تبعيّةٌ مُثبَّتةٌ عمداً). راجع `docker compose ps redis` قبل الاشتباه بـVault |
| **`worker-*` أو `outbox-relay` في حلقةٍ بـ`socket.gaierror: Temporary failure in name resolution`** | **ليس عطباً شبكيّاً رغم شكل الرسالة**: المُجمِّع لم يُقلَع أصلاً. سُدَّ في [§3.111](../log/3.111.md) بإعلان `pgbouncer` في `depends_on` للخدمتين — فإن رأيتَه اليوم فأنت على `docker-compose.yml` أقدم من ذلك التاريخ، أو أقلعتَ الخدمة بـ`--no-deps`. العلاج الفوريّ في الحالتين: `docker compose up -d pgbouncer` (والخدمة تتعافى وحدها بـ`restart: unless-stopped`) |
| **`https://localhost` يرفض الاتّصال** | لم تُولَّد الشهادة: `docker compose up -d nginx-certs` ثمّ أعد تشغيل `nginx` |
| **نموّ ذاكرة Redis** | `XLEN stream.<وحدة>` — المجاري إلحاقيّة و`XACK` لا يحذف (§4.1). راجع `STREAM_MAXLEN` و`used_memory` |
| 401 دائماً | صلاحية توكن Firebase / `FIREBASE_PROJECT_ID` |
| صفر صفوف رغم وجود بيانات | لم يُضبط `app.workspace_id` (RLS) — تحقّق من `ExecutionContext`/`rls.py` |
| الأحداث لا تصل العمّال | حالة `outbox-relay`؛ `published_at` في `platform.outbox`؛ طول المجرى في Redis؛ **ووجود مجموعة المستهلك وتأخّرها** (`XINFO GROUPS stream.<وحدة>`). **ترتيب الإقلاع لم يعد سبباً محتملاً** (§4) |
| مهام عالقة | نموّ `stream.<m>.dlq`؛ راجع سبب الفشل والمحاولات |
| رفض اتصال Postgres | مرّ عبر PgBouncer (6432) لا 5432؛ حجم التجمّع |
| فشل الأسرار | صحّة AppRole (`VAULT_ROLE_ID`/`VAULT_SECRET_ID`) وتفعيل Transit ووجود مفتاح `tenant-secrets` |
| فشل ربط موصّل | `OAUTH_REDIRECT_BASE_URL`؛ صلاحية `refresh_token`؛ نقل MCP (http/sse فقط) |
| رفض عملية بـ429 usage | تجاوز حصّة/ميزانية — راجع `GET /usage` و`/usage/limits` (`USAGE_DEFAULT_LIMITS`) |
