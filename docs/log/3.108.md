# §3.108 — `stream-topology-plan.md` الخطوة 4: الإثبات الحيّ على Redis حقيقيّ (`live_redis`)

> **الخطّة:** [`stream-topology-plan.md`](../stream-topology-plan.md) §3 · الخطوة 4 · **2026‑08‑03**
> **يغيّر حالة النظام الحيّ؟** ⚠️ **جزئيّاً**: لا شيفرة إنتاجٍ تغيّرت ولا حاويةَ ولا هجرة — لكنّ الاختبارَين الحيَّين ينشئان مفاتيحَ Redis قصيرة العمر (مجرًى ومجموعةٌ باسمَين عشوائيَّين لكلّ تشغيلة) على Redis المحلّي الحقيقيّ ويتلفانها في `finally` (`xgroup_destroy` + `delete`) في كلّ تشغيلة — بلا `FLUSH` وبلا لمس أيّ مفتاحٍ آخر. وبرهان الفشل (§3 أدناه) عدّل `src/app/workers/bootstrap.py` **مؤقّتاً** (سطرٌ واحد) ثمّ أعاده حرفيّاً، مُتحقَّقاً منه بـ`diff` صامت.
> **سابقتها:** [§3.107](3.107.md) (`stream-topology-plan.md` الخطوة 3 — المُرحّل يضمن المجموعات قبل أوّل نشر).

---

## 1. المشكلة

الخطوات 1–3 أصلحت الجذر وقاسته بالوحدة: مستهلكٌ زائفٌ يسجّل الترتيب، لا Redis حقيقيّ. معيارا القبول 2 و6 من الخطّة يطلبان قياساً حيّاً بالذات: عاملٌ حقيقيٌّ (§1‑أ) وهذا الاختبار (§4 بند 6) — «اختبار الخطوة 4 يسقط على `814cb59` وينجح بعد الخطوة 3». حتّى هذه الخطوة لا اختبار واحد شغّل `build_relay_from_env()` الحقيقيّة فوق Redis حيّ وقرأ منه فعلاً.

## 2. القرار

### 2‑أ · مسألة عنوان Redis — لم تُفترَض، قِيست

`build_relay_from_env` يحلّ عميله عبر `load_settings()` (`REDIS_URL`)، و`.env`/`.env.example` المُودَعان في المستودع يثبّتان `REDIS_URL=redis://redis:6379/0` — اسم مضيفٍ خاصٌّ بشبكة Docker. قِسنا هذا مباشرةً قبل كتابة أيّ اختبار:

```
$ .venv/bin/python -c "from app.infrastructure.config.env_settings import load_settings; print(load_settings().redis.url)"
redis://redis:6379/0
```

بينما تُخرِج مِحضنة `live_redis` (`tests/integration/conftest.py:621`) `TEST_REDIS_URL` أو الافتراضيّ `redis://127.0.0.1:6379/0` — عنوانان مختلفان بلا شرط. فكلا الاختبارَين يبدأ بـ`monkeypatch.setenv("REDIS_URL", live_redis)` **قبل** أوّل نداءٍ لـ`build_relay_from_env()`، مسجَّلاً في docstring الملفّ لماذا هذا السطر ضروريّ لا زخرفة: بدونه كان الاختبار سيهيّئ المجموعات على خادمٍ ويقرأ من آخر — وقد ينجح بالحظّ (‏Redis محلّيّ آخر هادئٌ هو الآخر) لا لأنّ الإصلاح عمل فعلاً.

### 2‑ب · الاختبار الأوّل — الإصلاح عبر الإغلاق الحقيقيّ

`tests/integration/test_relay_ensures_groups_live.py::test_ensure_topology_then_publish_delivers_all_three_entries`:

1. `STATIC_CONSUMER_TOPOLOGY` مُبدَّلةٌ عند `app.workers.bootstrap.STATIC_CONSUMER_TOPOLOGY` (حيث يقرؤها `build_relay_from_env` فعلاً — لا عند تعريفها في `topology.py`؛ `from ... import` يربط اسماً جديداً في مساحة اسم `bootstrap.py`) بزوجٍ واحدٍ جديدٍ كلّيّاً (`stream.test.<uuid7>` / `cg.test.<uuid7>`).
2. `build_relay_from_env()` الحقيقيّة ← `await ensure_topology()`.
3. **ثمّ** ثلاث `XADD` على المجرى.
4. **ثمّ** مستهلكٌ ينضمّ إلى المجموعة أوّل مرّة ويقرأ.
5. التوقُّع: **الثلاث** بالضبط، وتُقارَن الحمولات حرفاً بحرف — لا مجرّد «غير فارغة».

### 2‑ج · الاختبار الثاني — العطب القديم بآليّته الحقيقيّة

`test_publish_then_ensure_topology_delivers_nothing`: نفس المجرى الجديد، لكنّ الترتيب معكوس — ثلاث `XADD` **أوّلاً**، ثمّ `ensure_topology()` (أي `xgroup_create(..., id="$")`)، ثمّ القراءة. **التوقُّع: صفر مدخلات بالضبط.** وحارسُ الحارس: `XLEN` على المجرى = 3 **قبل** `ensure_topology()` — يثبت أنّ «صفراً» يعني «المجموعة وُلدت بعد ثلاث مدخلاتٍ حقيقيّة»، لا «لم يُنشر شيءٌ قطّ».
