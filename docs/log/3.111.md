# §3.111 — سدُّ ثغرة `depends_on`: `pgbouncer` صار تبعيّةً **مُعلَنة** لـ`worker` و`outbox-relay`

> **الأصل:** [`stream-topology-plan.md`](../stream-topology-plan.md) **§6‑هـ** (ملاحظةٌ خارج نطاق الخطّة، كُتبت حين اكتُشف العطب) · **2026‑08‑03**
> **يغيّر حالة النظام الحيّ؟** **لا.** لم تُقلَع حاويةٌ واحدة ولم تُبنَ صورة؛ الإثبات كلّه بـ`docker compose config` و`--dry-run` (محاكاةٌ تطبع خطّة الإقلاع ولا تُنشئ شيئاً). ولا سطرَ منطقٍ واحد تحت `src/`: `git diff --stat -- src/ tests/` **فارغ**.
> **سابقتها:** [§3.110](3.110.md) — الخطوة 6 من الخطّة، وهي التي كشفت هذا العطب عرَضاً وامتنعت عن إصلاحه احتراماً لمعيار القبول 8.

---

## 1. العطب في جملةٍ واحدة

الملفّ `docker-compose.yml` هو **المصدر الوحيد المُعلَن لترتيب الإقلاع** — و[`08 §2`](../design/08-local-runbook.md) يقول ذلك حرفيّاً: «الترتيب كلّه مُرمَّزٌ في `depends_on`». وخدمتان تصلان قاعدة البيانات **عبر المُجمِّع حصراً**:

```yaml
# worker
DATABASE_URL: postgresql+asyncpg://app_rw:...@pgbouncer:6432/...
# outbox-relay
DATABASE_URL: postgresql+asyncpg://outbox_relay:...@pgbouncer:6432/...
```

ولم تُعلن أيٌّ منهما `pgbouncer` في `depends_on`. فحين يُسمّى اسمُ خدمةٍ بعينها في الأمر — وهو **ما يأمر به الدليل نفسه** في [`08 §4`](../design/08-local-runbook.md):

```bash
WORKER=memory docker compose --profile workers up -d worker
docker compose up -d outbox-relay
```

يُقلع Compose **المطلوبَ وما أعلن أنّه يحتاجه فقط**، فلا يُقلع المُجمِّع، فتستيقظ العمليّة تبحث عن مضيفٍ لا وجود له:

```
socket.gaierror: [Errno -3] Temporary failure in name resolution
```

⚠️ **ولا يظهر على `docker compose up -d` الكامل إطلاقاً** — المُجمِّع يقلع مع الجميع بلا حاجةٍ إلى أن يُطلَب. ولهذا بالضبط عاش العطب من الطور الأوّل إلى اليوم بلا أن يراه أحد.

## 2. لماذا هو أخبثُ من حجمه

| | |
|---|---|
| **الرسالة تُضلّل** | «اسمٌ لا يُحلّ» صيغةُ عطبٍ **شبكيّ**، فيذهب القارئ يفتّش في الشبكات والأسماء والمنافذ — والسببُ سطران ناقصان في قائمة الانتظار. **وهذا ما وقع فعلاً**: ضاع الطور أ من [§3.110](3.110.md) كلّه قبل أن يتبيّن السبب |
| **يشفى وحده فيبدو متقطّعاً** | `restart: unless-stopped` ⇒ متى أقلع أحدٌ المُجمِّعَ لأيّ سببٍ آخر، تعافت الخدمة بلا تدخّل. عطبٌ يظهر ويختفي بلا نمط |
| **يُكذّب الملفَّ في وعده** | وهذا أخطرها. من يقرأ `depends_on` ليعرف ماذا تحتاج الخدمة، يقرأ **نقصاً** لا يُنبّهه إليه شيء |

---

## 3. ⚠️ تصحيحٌ لِما قالته §6‑هـ نفسها — الثقب **خدمتان لا واحدة**

كُتب في §6‑هـ من الخطّة (وأُعيد في رأس [`implementation-status.md`](../implementation-status.md)) أنّ العطب في `outbox-relay`، وأنّ «`app`/`worker` لهما شبكاتُ تبعيّاتٍ أوسع تجرّ `pgbouncer` عرضاً». **والنصفان خاطئان:**

- **`app`** تُعلن `pgbouncer` **صراحةً** في `depends_on` منذ البداية — لا «عرضاً».
- **`worker`** لا تجرّه لا صراحةً ولا عرضاً: تبعيّاتها كانت `ollama-bridge` · `redis` · `embedding` · `migrate` · `vault-bootstrap`، ولا واحدةٌ منها تؤدّي إلى المُجمِّع (‏`migrate` تتّصل بـ`postgres` **مباشرةً** على 5432، وهذا موثَّقٌ ومقصود).

**مقيسٌ لا مُستنتَجاً** — محاكاةٌ على الملفّ كما كان قبل هذا الإصلاح حرفيّاً (`git show HEAD:docker-compose.yml`):

```
$ docker compose -f <الملفّ قبل الإصلاح> --profile workers --dry-run up -d worker | grep -c pgbouncer
0
```

⇒ **صفر**. الطريقان الموصى بهما في الدليل كلاهما كان معطوباً، لا أحدهما.

---

## 4. التغيير — سطران في كلّ خدمة، منسوخان من `app` حرفيّاً

```yaml
      pgbouncer:
        condition: service_started
```

`service_started` لا `_healthy`: **المُجمِّع لا يُعرِّف فحصَ صحّةٍ أصلاً**، و`app` تأخذ هذه الحافّة بهذا الشرط نفسه منذ الطور الأوّل. فالإصلاح يجعل الثلاثة **متّسقة**، لا كاملة (§7).

ومعهما تعليقٌ في `outbox-relay` يشرح العطب وسببَ الشرط، وإحالةٌ إليه من `worker` — كي لا يُحذف أحدهما يوماً بوصفه «تبعيّةً زائدة».

---

## 5. الإثبات — في الاتّجاهين، وبلا لمس النظام الحيّ

**(أ) الرسمُ المُركَّب بعد الإصلاح** (`docker compose config` — قراءةٌ خالصة):

```
app          ['embedding','migrate','minio','ollama-bridge','pgbouncer','redis','vault','vault-bootstrap']
outbox-relay ['migrate','pgbouncer','redis']
worker       ['embedding','migrate','ollama-bridge','pgbouncer','redis','vault-bootstrap']
```

**(ب) خطّة الإقلاع بعد الإصلاح** (`--dry-run`، محاكاةٌ لا تُنشئ شيئاً):

```
$ docker compose --dry-run up -d outbox-relay
 Container aizzak-pgbouncer-1 Created
 Container aizzak-outbox-relay-1 Created
 Container aizzak-postgres-1 Healthy
 Container aizzak-pgbouncer-1 Starting
 Container aizzak-pgbouncer-1 Started
 ...

$ WORKER=memory docker compose --profile workers --dry-run up -d worker
 Container aizzak-pgbouncer-1 Started
 Container aizzak-worker-1 Starting
 Container aizzak-worker-1 Started
```

⇒ المُجمِّع **يُنشأ ويُقلَع قبلهما**، على الطريقين.

**(ج) برهان الفشل — الملفّ نفسه قبل الإصلاح** (§0 قاعدة 3: يُبرهَن على العطب بآليّته لا بوصفه):

```
$ docker compose -f <الملفّ قبل الإصلاح> --dry-run up -d outbox-relay
 Container aizzak-postgres-1 Created
 Container aizzak-redis-1 Created
 Container aizzak-migrate-1 Created
 Container aizzak-outbox-relay-1 Created
 ...
```

⇒ **`pgbouncer` غائبٌ من الخطّة كلّها** — لا يُنشأ ولا يُقلَع. وهو بالضبط ما وقع حيّاً في [§3.110](3.110.md) §3‑ب.

## 6. الشرط الذي وضعته §6‑هـ على نفسها — **مُستوفًى**

نصّت §6‑هـ على أنّ العلاج «يجب أن يُقارَن بمسار RunPod (‏`supervisord`) قبل تثبيته». المقارنة جرت، ونتيجتها قاطعة: **مسار RunPod لا يعرف `pgbouncer` إطلاقاً.**

```
deploy/runpod/entrypoint.sh:94   DATABASE_URL=...@127.0.0.1:5432/...
deploy/runpod/entrypoint.sh:100  RELAY_DATABASE_URL=...@127.0.0.1:5432/...
deploy/runpod/bootstrap.sh:88    DATABASE_URL=...@127.0.0.1:5432/...
```

حاويةٌ واحدةٌ تصل Postgres مباشرةً على 5432، بلا مُجمِّعٍ في الصورة أصلاً. ⇒ التغيير **لا يمسّ ترتيب `supervisord` بحرف**، ولا يُنشئ فارقاً جديداً بين المسارين — بل يُلغي فارقاً كان قائماً: كان مسار Compose وحده هو المعرَّض للعطب.

---

## 7. ما لم يُصلَح — مُسمًّى صراحةً لئلّا يُظنّ منسيّاً

`condition: service_started` تعني أنّ الحاوية **بدأت**، لا أنّ المُجمِّع **صار يقبل اتّصالاً**. الفارق حقيقيّ: يبقى سباقٌ نظريٌّ ضيّق تُقلع فيه الخدمةُ ويفشل أوّل اتّصالٍ لها بـ«رُفض الاتّصال» بدل «اسمٌ لا يُحلّ».

ولم يُعالَج هنا **عمداً**: علاجه فحصُ صحّةٍ على `pgbouncer` يرفع الشرطَ إلى `service_healthy` في **ثلاث** خدمات — قرارٌ في طوبولوجيا الإقلاع أوسع من سدّ ثقبٍ مُعلَن، ولا يجوز أن يركب هذا الإصلاح خلسةً. والفارق العمليّ بين الحالين كبير: قبل الإصلاح كانت الخدمة تدور في حلقةٍ **بلا نهاية** لأنّ المضيف لا يوجد؛ بعده تُعيد المحاولةَ على مضيفٍ موجودٍ يقلع في ثوانٍ.

## 9. ما لم يُمَسّ

- **`src/` و`tests/`** — `git diff --stat` فارغٌ حرفيّاً. ولا اختبارٌ أُضيف أو حُذف.
- **`redis_streams.py:235`** — `xgroup_create(..., id="$", ...)` كما هو؛ لا صلةَ لهذا الإصلاح بالطوبولوجيا.
- **`deploy/`** — مسار RunPod كما هو (§6).
- **طوبولوجيا `docker-compose.yml` الأخرى** — لا خدمةَ أُضيفت أو حُذفت، ولا متغيّرَ بيئةٍ تغيّر، ولا صورةَ وسمُها تبدّل. التغيير كلّه **حوافُّ `depends_on` وتعليقاتُها**.
- **`docs/log/*`** السابق — صفر حذف؛ هذه مدخلةٌ **جديدة**، وما قبلها لم يُمَسّ. والتصحيح في §3 أعلاه **مكتوبٌ هنا**، لا مُعاداً كتابته في [§3.110](3.110.md).

## 11. الحالة

✅ **مُنجَز** — 🔵 بانتظار مراجعة المستخدم. غيرُ مُلتزَم (المستخدم يلتزم بنفسه).

**الدرس المسجَّل:** عنوانٌ في `DATABASE_URL` **ليس** إعلانَ تبعيّة. الأوّل يقول «سأكلّم هذا»، والثاني يقول «لا تُقلعني قبله» — وغيابُ الثاني مع حضور الأوّل عطبٌ **صامتٌ على الطريق الشائع، صاخبٌ على الطريق الموصى به**، وهذا أسوأ ترتيبٍ ممكن: لا يراه من يُقلع المكدّس كلّه، ويصطدم به من يتبع الدليل حرفيّاً.
