# نشر AIZZAK على خادم Linux محلّيّ — دليلٌ خطوةً بخطوة

> **لمن هذه الوثيقة؟** لمن لم يسبق له نقل تطبيقٍ إلى خادمٍ من قبل. كلّ أمرٍ هنا مكتوبٌ كاملاً وجاهزٌ للّصق، وكلّ ملفٍّ ومتغيّرٍ مذكورٌ باسمه وقيمته وسببه.
>
> **علاقتها بباقي الوثائق:** [`quickstart.md`](quickstart.md) يشرح التشغيل على **جهاز التطوير هذا** (‏WSL، ببنية Compose ومنافذ مضيف مزاحة، مع Ollama أصلي داخل WSL). هذه الوثيقة تشرح النقل إلى **خادمٍ نظيفٍ منفصل** لا يوجد عليه شيءٌ بعد. و[`design/08-local-runbook.md`](design/08-local-runbook.md) هو المرجع **المُلزِم** للقرارات التشغيليّة. عند أيّ تعارضٍ فـ08 هي الصحيحة. أمّا [`deploy-runpod.md`](deploy-runpod.md) فيشرح منصّةً **لا تدعم `docker compose`**؛ هنا العكس تماماً.
>
> **آخر مطابقةٍ مع الواقع: 2026‑07‑25.**

## 0) اقرأ هذا أوّلاً — الخبر الجيّد، والفرق الوحيد

على عكس RunPod، **خادم Linux العاديّ يدعم `docker compose` دعماً كاملاً.** هذا يعني أنّك **لا تحتاج أيّ صورةٍ خاصّة ولا أيّ إعادة هيكلة**: المشروع يُقلَع بالأمر نفسه الذي يعمل على جهاز التطوير:

```bash
docker compose up -d
```

هذا الأمر الواحد يبني ويشغّل المكدّس كما صُمّم بالضبط — الطوبولوجيا نفسها، الملفّات نفسها، الترتيب نفسه. **هذا هو المسار الأقرب إلى تصميم المشروع**، ولا انحرافات فيه كتلك التي فرضتها RunPod.

### الفرق الوحيد الذي يلزمك ضبطه بيدك

هناك **شيءٌ واحد** لا يعمل تلقائيّاً على خادم Linux «خام» (‏Docker Engine) بينما يعمل على جهاز التطوير (‏Docker Desktop / WSL): وصول الحاويات إلى **Ollama** عبر الاسم `host.docker.internal`.

| البيئة | هل يُحَلّ `host.docker.internal` تلقائيّاً؟ |
|---|---|
| Docker Desktop (‏Mac / Windows / WSL) — جهاز التطوير | ✅ نعم، مبنيٌّ في المنتج |
| Docker Engine على خادم Linux (‏`apt install`, `get.docker.com`) | ⛔ **لا** — يجب ربطه يدويّاً |

المشروع يشير إلى Ollama بـ`OLLAMA_BASE_URL=http://host.docker.internal:11434` (في `.env.example` و`docker-compose.yml`)، ولا يوجد `extra_hosts` يربطه، لأنّ جهاز التطوير لا يحتاجه. **على خادمك ستحتاجه**، و[§7](#7-الخطوة-5--ollama-على-لينكس-الفرق-الوحيد) يعالجه بطريقتين. هذا هو الانحراف الوحيد؛ كلّ ما عداه يعمل كما هو.

> 💡 خارج ذلك، الأمر الثاني الذي يلزمك تعديله ليس «عطلاً» بل **إعداد**: جدول التوجيه `PROVIDER_ROUTING` في `.env.example` يشير افتراضيّاً إلى مزوّدٍ سحابيّ (‏`openai`) محجوبٍ بالمفاتيح. على خادمٍ محلّيٍّ تحوّله إلى **Ollama** المحلّيّ ([§6](#6-الخطوة-4--ملء-env)).

## 1) ما ستحصل عليه في نهاية هذا الدليل

خادمٌ لينكسيٌّ واحد، يشغّل بأمرٍ واحد **ثماني عشرة حاوية** (أربع عشرة تبقى تعمل — منها **العمّال الثلاثة** `memory` و`knowledge` و`media` ([§3.133](log/3.133.md) ثمّ [§3.134](log/3.134.md)) — وأربعٌ «لمرّةٍ واحدة» تنفّذ مهمّتها ثمّ تخرج بنجاح). **لا `profile` في الملفّ بعد الآن**، فلا حاوية اختياريّة. (‏العددان المكتوبان هنا سابقاً «أربع عشرة» ثمّ «سبع عشرة + واحدة اختياريّة» بائدان: الأوّل لم يكن يعدّ `ollama-bridge`، والثاني سبق قياسَ إقلاع `media`.)

```
┌───────────────── خادم Linux (docker compose up -d) ─────────────────┐
│  شبكة Docker الداخليّة  (aizzak_default)                             │
│                                                                     │
│  ┌── منشورٌ على المضيف — تفتحه في الجدار الناريّ ───────────────┐    │
│  │  nginx        80 / 443   ← الواجهة العامّة (‏TLS ذاتيّ التوقيع)  │    │
│  │  minio API    19000      ← إلزاميّ للروابط المُوقَّعة مسبقاً     │    │
│  │  minio console 19001     ← لوحة إدارة (‏أغلقها في الإنتاج)      │    │
│  └───────────────────────────────────────────────────────────────┘    │
│                                                                     │
│  ┌── داخليٌّ فقط — يتخاطب بالاسم على شبكة Docker ────────────────┐   │
│  │  app :8000        postgres :5432     pgbouncer :6432          │   │
│  │  redis :6379      qdrant :6333       vault :8200              │   │
│  │  embedding :8080  outbox-relay (بلا منفذ)  ollama-bridge      │   │
│  │  worker-memory · worker-knowledge · worker-media               │   │
│  │      (‏الثلاثة افتراضيّون، بلا منفذ — لا profile)                │   │
│  └───────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  Ollama :11434  ← تضيفه أنت: خدمةً في compose، أو على المضيف (§7)    │
│                                                                     │
│  أحجام Docker الدائمة:  postgres-data · redis-data · minio-data ·    │
│                         qdrant-data · vault-data · vault-init        │
│                         (+ ollama-data لو أضفته خدمة)                │
└─────────────────────────────────────────────────────────────────────┘
```

### الحاويات الأربع «لمرّةٍ واحدة» — ليست أعطالاً حين تراها `Exited`

| الحاوية | ماذا تفعل | ثمّ |
|---|---|---|
| `nginx-certs` | تولّد شهادة TLS ذاتيّة التوقيع (‏تتخطّى نفسها إن وُجدت شهادة) | تخرج `0` |
| `vault-bootstrap` | تفعّل KV+Transit وتبذر الأسرار وتنشئ AppRole | تخرج `0` |
| `minio-bootstrap` | تنشئ دلو `workspace-files` | تخرج `0` |
| `migrate` | تشغّل **إحدى عشرة سلسلة هجرات + المنح** (`app.ops.provision`) | تخرج `0` |

> ⚠️ رؤية هذه الأربع بحالة `Exited (0)` في `docker compose ps` هي **الحالة الصحيحة**، لا عطل. `app` لا يقلع إلّا بعد أن تخرج `migrate` و`vault-bootstrap` بنجاح (‏`depends_on: service_completed_successfully`).

### جدول المنافذ — ما يُنشر على المضيف وما يبقى داخليّاً

| الخدمة | داخل الشبكة | على المضيف | يجب أن يكون عامّاً؟ |
|---|---|---|---|
| nginx | 80 / 443 | **80 / 443** | ✅ نعم — الواجهة |
| minio (‏API) | 9000 | **19000** | ⚠️ نعم إن رفع المتصفّح ملفّاتٍ مباشرةً (الروابط المُوقَّعة) |
| minio (‏كونسول) | 9001 | 19001 | ⛔ **لا** — أغلقه في الإنتاج |
| postgres | 5432 | 15432 | ⛔ **لا** ([§10.2](#102-المنافذ-الداخليّة-والجدار-الناريّ--docker-يتخطّى-ufw)) |
| pgbouncer | 6432 | 16432 | ⛔ لا |
| redis | 6379 | 16379 | ⛔ لا |
| qdrant | 6333 | 16333 | ⛔ لا |
| vault | 8200 | 18200 | ⛔ لا |
| embedding | 8080 | **غير منشور** (`expose`) | داخليّ عمداً |
| app | 8000 | **غير منشور** (خلف nginx) | داخليّ |

> ⚠️ المنافذ المُزاحة (‏15432، 16432…) موروثةٌ من جهاز التطوير حيث تعمل خدماتٌ أصليّةٌ على المنافذ القانونيّة ويجب تفادي التصادم. **على خادمٍ نظيفٍ لا تصادم**، فالإزاحة غير ضارّة — لكنّ **نشرها على المضيف أصلاً خطرٌ أمنيّ** يعالجه [§10.2](#102-المنافذ-الداخليّة-والجدار-الناريّ--docker-يتخطّى-ufw). اقرأه قبل أن تفتح الخادم للإنترنت.

## 2) المتطلّبات المسبقة

### 2.1 الخادم

| البند | الحدّ الأدنى | الموصى به | لماذا |
|---|---|---|---|
| نظام التشغيل | Ubuntu 22.04 / Debian 12 | Ubuntu 24.04 LTS | أوامر هذا الدليل مكتوبةٌ لـ`apt` |
| المعالج | 4 أنوية | 8 أنوية | خدمة التضمين + Postgres + Ollama تتنافس على المعالج |
| الذاكرة | 8 ج.ب | **16 ج.ب** | ‏torch (‏التضمين) + Ollama (‏نموذج اللغة) نهِمان للذاكرة |
| القرص | 40 ج.ب | 60 ج.ب+ | الصور ≈ 6–8 ج.ب، والبيانات + نموذج Ollama تنمو |
| المعمار | x86‑64 | x86‑64 | الصور القاعديّة كلّها `amd64` |

> 💡 **GPU اختياريّ ولا يلزم لإقلاع التطبيق.** المكوّن الوحيد الذي يستفيد منه هو Ollama (توليد النصّ). كلّ ما عداه — بما فيه خدمة التضمين — يعمل على المعالج فقط (`services/embedding/requirements.txt` يسحب torch من فهرس عجلات المعالج صراحةً). بلا GPU يعمل كلّ شيء، لكنّ ردّ الوكيل يكون أبطأ.

### 2.2 ما تحتاج تجهيزه قبل البدء

1. **وصول SSH إلى الخادم** بصلاحيّة `sudo`. لو استأجرته لتوّك من مزوّدٍ (‏Hetzner، DigitalOcean، Contabo…) فلديك `root@<عنوان-الخادم>` وكلمة سرٍّ أو مفتاح SSH.
2. **Firebase Project ID** — من [console.firebase.google.com](https://console.firebase.google.com) ← مشروعٌ (‏أو مشروعٌ قائم) ← `⚙️ Project settings → General` ← انسخ **Project ID** (مثل `aizzak-prod-12345`).
3. **اسم نطاقٍ (اختياريّ لكنّه مستحسن)** يشير إلى عنوان IP خادمك (سجلّ `A`). بدونه ستصل بالتطبيق عبر عنوان IP مباشرةً وبشهادةٍ ذاتيّة التوقيع.

> ⚠️ `FIREBASE_PROJECT_ID` **إلزاميّ ولا بديل عنه**: `FirebaseAuth` يفشل فشلاً سريعاً عند الإنشاء على قيمةٍ فارغة، فالعَرَض ليس «مصادقةٌ لا تعمل» بل **تطبيقٌ لا يقلع إطلاقاً**.

### 2.3 المنافذ التي ستفتحها في الجدار الناريّ

| المنفذ | لماذا |
|---|---|
| `22` | SSH (‏لإدارة الخادم) |
| `80` · `443` | واجهة التطبيق عبر nginx |
| `19000` | واجهة MinIO — **إن كان المتصفّح يرفع/ينزّل ملفّاتٍ مباشرةً** عبر الروابط المُوقَّعة |

كلّ ما عدا هذه **يجب ألّا يكون مكشوفاً للإنترنت** ([§10.2](#102-المنافذ-الداخليّة-والجدار-الناريّ--docker-يتخطّى-ufw)).

## 3) الخطوة 1 — تجهيز الخادم

اتّصل بخادمك:

```bash
ssh root@<عنوان-الخادم>
```

### 3.1 حدّث النظام وثبّت الأدوات الأساسيّة

```bash
sudo apt update && sudo apt -y upgrade && sudo apt -y install git curl ca-certificates
```

### 3.2 ثبّت Docker Engine + إضافة Compose

السكربت الرسميّ يثبّت المحرّك وإضافة `compose v2` معاً:

```bash
curl -fsSL https://get.docker.com | sh
```

تحقّق:

```bash
sudo docker --version && sudo docker compose version
```

يجب أن ترى `Docker version 2x.x` و`Docker Compose version v2.x`.

### 3.3 شغّل Docker مع كلّ إقلاعٍ للنظام

```bash
sudo systemctl enable --now docker
```

> ⚠️ هذه الخطوة **ليست تجميليّة**: بدونها، بعد كلّ إعادة تشغيلٍ للخادم لن يقلع Docker أصلاً، فلن يقلع تطبيقك. ومع ذلك تبقى قاعدةٌ ذهبيّةٌ لاحقة (‏[§11.4](#114--فخّ-إعادة-تشغيل-الخادم-اقرأه-قبل-أوّل-reboot)): بعد أيّ إعادة تشغيلٍ استعمل `docker compose up -d`، لا `docker start`.

### 3.4 (مستحسن) شغّل Docker بلا `sudo`

```bash
sudo usermod -aG docker $USER
```

ثمّ **اخرج من الجلسة وأعد الدخول** (`exit` ثمّ `ssh` من جديد) ليسري التغيير. بعدها تعمل أوامر `docker` بلا `sudo`. (بقيّة هذا الدليل تكتب الأوامر بلا `sudo`؛ أضِفه إن تخطّيت هذه الخطوة.)

## 4) الخطوة 2 — نقل المشروع إلى الخادم

طريقتان. اختر واحدة.

### الطريقة (أ): `git clone` — إن كان مشروعك في مستودعٍ بعيد

```bash
git clone <رابط-مستودعك> /opt/aizzak && cd /opt/aizzak
```

### الطريقة (ب): `rsync` من جهازك — إن كان محلّيّاً فقط

على **جهازك** (لا الخادم)، من داخل WSL:

```bash
rsync -av --exclude '.venv' --exclude '.git' --exclude '.env' \
      /home/AIZZAK/ root@<عنوان-الخادم>:/opt/aizzak/
```

> ⚠️ **`--exclude '.venv'` ليس تحسيناً بل ضرورة**: بيئة `.venv` (‏≈ 460 م.ب) مبنيّةٌ لمعالج جهازك ونظامه ولا تصلح للخادم — ولا يحتاجها أصلاً، فالحاويات تبني بيئتها بنفسها. واستبعاد `.env` مقصود: **الأسرار لا تُنقل؛ ستنشئها على الخادم في [§5](#5-الخطوة-3--توليد-كلمات-السرّ)**.

> 💡 لاحظ أنّ `.env` **مُتَجاهَلٌ في git**، فالطريقة (أ) لن تجلبه أصلاً. في الحالتين تنشئ `.env` جديداً على الخادم. هذا مقصود: نسخة الأسرار على الخادم مستقلّةٌ عن جهازك.

بعد النقل، كن على الخادم داخل مجلّد المشروع:

```bash
cd /opt/aizzak
```

## 5) الخطوة 3 — توليد كلمات السرّ

ثماني قيمٍ سرّيّة. **لا تخترعها يدويّاً ولا تعِد استخدام كلمةٍ قديمة.** ولّدها بأمرٍ واحدٍ على الخادم:

```bash
for k in POSTGRES_SUPERUSER_PASSWORD AIZZAK_OWNER_PASSWORD APP_RW_PASSWORD OUTBOX_RELAY_PASSWORD RETENTION_SWEEPER_PASSWORD METRICS_READER_PASSWORD MINIO_ROOT_PASSWORD; do echo "$k=$(openssl rand -hex 24)"; done; echo "MINIO_ROOT_USER=aizzak-minio"
```

انسخ المخرجات الثماني إلى مكانٍ آمنٍ مؤقّتاً؛ ستلصقها في `.env` في الخطوة التالية.

> ⚠️ **استعمل `openssl rand -hex` تحديداً، ولا تضع رموزاً خاصّة في كلمات السرّ.** كلمات سرّ Postgres والمُرحّل تدخل في **رابط اتّصالٍ** (`postgresql+asyncpg://user:PASSWORD@host/db`)، ورموزٌ مثل `@` `:` `/` `%` `#` تكسر تحليل الرابط. الأحرف السُّداسيّة العشريّة التي يولّدها `openssl rand -hex` آمنةٌ بالبناء.

**لماذا سبع قيمٍ وليست واحدة؟** لأنّ الفصل بين أدوار قاعدة البيانات هو **ضمانة عزل المستأجرين** نفسها، لا بيروقراطيّة:

| الدور | ما يملكه |
|---|---|
| `postgres` (المستخدم الفائق) | تهيئة العنقود وإنشاء الأدوار فقط. لا يخدم طلباً |
| `aizzak_owner` | المُهاجِر ومالك الجداول. يشغّل الهجرات. **لا يخدم أيّ طلب** |
| `app_rw` | ما يتّصل به التطبيق والعمّال. `NOINHERIT`، بلا `BYPASSRLS`، ليس مالكاً ⇒ **سياسة RLS هي التي تحصره** في مساحة عملٍ واحدة |
| `outbox_relay` | `SELECT/UPDATE` على `platform.outbox` ولا شيء غيرها |
| `retention_sweeper` | `SELECT/DELETE` فقط على ثلاثة جداولٍ غير محدودة (`platform.outbox`/`platform.processed_events`/`platform.idempotency_keys`) — مكنسة احتفاظٍ تُشغَّل يدويّاً (`python -m app.ops.retention`)، لا خدمةً دائمة |
| `metrics_reader` | `SELECT` وحيدة على `platform.outbox` — قراءة `/metrics` (‏P1‑3)، خدمةٌ دائمة داخل `app` |
| `MinIO root` | تخزين الكائنات |

> الأدوار الخمسة لقاعدة البيانات تُنشأ **مرّةً واحدةً عند تهيئة العنقود** (`deploy/postgres/initdb/10-roles.sh`) لأنّ `CREATE ROLE` صلاحيّةُ عنقودٍ لا يملكها `aizzak_owner` عمداً. أمّا **المنح** فتأتي بعد الهجرات (`app.ops.provision`) لأنّها تحتاج الجداول موجودةً أوّلاً.

## 6) الخطوة 4 — ملء `.env`

انسخ القالب:

```bash
cp .env.example .env
```

ثمّ حرّره:

```bash
nano .env
```

(لو لم يكن `nano` مثبّتاً: `sudo apt -y install nano`، أو استعمل `vim`.)

### 6.1 القيم التي **يجب** أن تغيّرها

| المفتاح | القيمة |
|---|---|
| `POSTGRES_SUPERUSER_PASSWORD` | من [§5](#5-الخطوة-3--توليد-كلمات-السرّ) |
| `AIZZAK_OWNER_PASSWORD` | من §5 |
| `APP_RW_PASSWORD` | من §5 |
| `OUTBOX_RELAY_PASSWORD` | من §5 |
| `RETENTION_SWEEPER_PASSWORD` | من §5 |
| `MINIO_ROOT_USER` | `aizzak-minio` |
| `MINIO_ROOT_PASSWORD` | من §5 |
| **`FIREBASE_PROJECT_ID`** | معرّف مشروعك (‏مثل `aizzak-prod-12345`). ⚠️ **فارغه = تطبيقٌ لا يقلع** |

### 6.2 القيمة التي **يجب** أن تحوّلها إلى Ollama

في `.env.example` يشير جدول التوجيه إلى مزوّدٍ سحابيّ محجوب. **استبدل سطر `PROVIDER_ROUTING` كاملاً** بهذا (مزوّد Ollama المحلّيّ):

```
PROVIDER_ROUTING={"llm":{"default":{"provider":"ollama","model":"gemma3:1b"}},"embedding":{"default":{"provider":"embedding-local","model":"sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"}}}
```

### 6.3 القيم التي تضبطها حسب طريقة Ollama والعنوان العامّ

| المفتاح | القيمة | متى |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://ollama:11434` | إن أضفت Ollama **خدمةً في compose** ([§7.1](#71-الطريقة-الموصى-بها-ollama-خدمةً-في-compose)) — **الموصى به** |
| `OLLAMA_BASE_URL` | `http://host.docker.internal:11434` | إن ثبّت Ollama **على المضيف** ([§7.2](#72-البديل-ollama-على-المضيف)) |
| `MINIO_PUBLIC_ENDPOINT` | `<عنوان-خادمك>:19000` | العنوان الذي **يصله المتصفّح**؛ ليس `localhost` |
| `MINIO_PUBLIC_SECURE` | `false` | إن كان 19000 عبر HTTP عاديّ (‏الحالة الأبسط) |
| `OAUTH_REDIRECT_BASE_URL` | `https://<نطاقك>` | فقط إن استعملت موصّلات OAuth (‏وحدة `integrations`) |
| `WORKER` | `memory` | **لا أثر له على Compose بعد [§3.133](log/3.133.md)** — لكلّ عاملٍ خدمتُه بقيمةٍ حرفيّة. يبقى للحاويّة الواحدة (‏RunPod) و`python -m` المجرّد ([§8.3](#83-العمّال-والمُرحّل)) |

> ⚠️ `MINIO_PUBLIC_ENDPOINT` **ليس تجميلاً**: الروابط المُوقَّعة مسبقاً (‏presigned) تُوقَّع بـSigV4 **على اسم المضيف**. رابطٌ وُقِّع على `minio:9000` (‏الاسم الداخليّ) أو `localhost:19000` **لا يصلح لمتصفّحٍ على جهازٍ آخر**، ولا يمكن تصحيحه بعد التوقيع — لا بـnginx ولا بجراحة نصوص. ضعه على العنوان الذي يصل إليه المستخدم فعلاً، وافتح 19000 في الجدار الناريّ.

### 6.4 ما لا تلمسه — وهذا مقصود

`DATABASE_URL` · `REDIS_URL` · `MINIO_ENDPOINT` · `QDRANT_URL` · `VAULT_ADDR` · `EMBEDDING_SERVICE_URL` · `EVENT_STREAM_PREFIX` وبقيّة الضبط. `docker-compose.yml` يركّبها لكلّ عمليّةٍ من الأسرار أعلاه؛ تركها كما هي هو الصحيح. و`VAULT_TOKEN` اتركه **فارغاً** كما في `.env.example` (‏وضع AppRole — لا توكن dev بعد الآن) — لكن **اقرأ تحذير Vault في [§10.1](#101--vault-دائمٌ-الآن--واقرأ-هذا-قبل-أوّل-اعتمادٍ-حقيقيّ)** قبل أيّ استخدامٍ حقيقيّ.

احفظ الملفّ (‏في `nano`: `Ctrl+O` ثمّ `Enter` ثمّ `Ctrl+X`).

## 7) الخطوة 5 — Ollama على لينكس (الفرق الوحيد)

هذا هو الشيء الوحيد الذي لا يعمل تلقائيّاً على خادمٍ خام ([§0](#0-اقرأ-هذا-أوّلاً--الخبر-الجيّد-والفرق-الوحيد)). اختر طريقةً واحدة.

### 7.1 الطريقة الموصى بها: Ollama خدمةً في compose

الأبسط والأكثر متانةً — كلّ شيءٍ داخل `docker compose`، بلا أيّ عبثٍ بشبكة المضيف، ويقلع تلقائيّاً مع بقيّة المكدّس.

أنشئ ملفّاً باسم `docker-compose.override.yml` **بجانب** `docker-compose.yml` (‏Compose يدمجه تلقائيّاً):

```bash
nano docker-compose.override.yml
```

والصق فيه:

```yaml
# إضافة Ollama إلى المكدّس على خادم Linux.
# Compose يدمج هذا الملفّ تلقائيّاً فوق docker-compose.yml.
services:
  ollama:
    image: ollama/ollama:0.5.7   # ثبّت وسماً محدّداً؛ راجع أحدث وسمٍ ثابت على hub.docker.com/r/ollama/ollama/tags
    volumes:
      - ollama-data:/root/.ollama
    restart: unless-stopped
    # ── GPU اختياريّ: أزِل التعليق فقط إن ثبّتّ nvidia-container-toolkit ──
    # deploy:
    #   resources:
    #     reservations:
    #       devices:
    #         - driver: nvidia
    #           count: all
    #           capabilities: [gpu]

volumes:
  ollama-data:
```

مع هذه الطريقة يكون `OLLAMA_BASE_URL=http://ollama:11434` في `.env` ([§6.3](#63-القيم-التي-تضبطها-حسب-طريقة-ollama-والعنوان-العامّ)). الاسم `ollama` يُحَلّ تلقائيّاً على شبكة Docker — لا حاجة لـ`host.docker.internal` إطلاقاً.

**سحب النموذج** (بعد الإقلاع في [§8](#8-الخطوة-6--الإقلاع)):

```bash
docker compose exec ollama ollama pull gemma3:1b
```

### 7.2 البديل: Ollama على المضيف

اختره إن أردت مشاركة Ollama بين مشاريع، أو كان GPU مضبوطاً على المضيف مسبقاً.

**1. ثبّت Ollama:**

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

**2. اجعله يستمع على كلّ الواجهات** (افتراضيّاً يستمع على `127.0.0.1` فقط، فلا تصله الحاويات):

```bash
sudo systemctl edit ollama
```

أضف في المحرّر الذي يفتح:

```ini
[Service]
Environment="OLLAMA_HOST=0.0.0.0:11434"
```

ثمّ:

```bash
sudo systemctl daemon-reload && sudo systemctl restart ollama
```

**3. اربط `host.docker.internal`** — أنشئ `docker-compose.override.yml` يربطه للخدمتين اللتين تناديان نموذج اللغة:

```yaml
services:
  app:
    extra_hosts:
      - "host.docker.internal:host-gateway"
  worker-memory:
    extra_hosts:
      - "host.docker.internal:host-gateway"
  worker-knowledge:
    extra_hosts:
      - "host.docker.internal:host-gateway"
  worker-media:
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

مع هذه الطريقة يبقى `OLLAMA_BASE_URL=http://host.docker.internal:11434` (‏قيمة `.env.example` الافتراضيّة).

**4. اسحب النموذج على المضيف:**

```bash
ollama pull gemma3:1b
```

> ⚠️ إن استعملت `ufw`: اسمح لشبكة Docker بالوصول إلى المنفذ: `sudo ufw allow from 172.16.0.0/12 to any port 11434 proto tcp`. وإلّا رُفض اتّصال الحاوية بـOllama رغم أنّه يعمل.

> ⚠️ **لا تجمع الطريقتين.** ملفٌّ واحدٌ `docker-compose.override.yml` فقط. اختر §7.1 **أو** §7.2.

## 8) الخطوة 6 — الإقلاع

### 8.1 ابنِ الصور (البناء الأوّل بطيء)

```bash
docker compose build
```

> ⏱️ **البناء الأوّل: 10–25 دقيقة.** أثقل خطوة هي صورة `embedding`: تثبّت `torch` (‏≈ 900 م.ب) و**تخبز أوزان نموذج التضمين داخل الصورة** (‏MiniLM متعدّد اللغات، ≈ 250–470 م.ب). مقابل ذلك: الحاوية بعدها لا تنادي `huggingface.co` أبداً (`HF_HUB_OFFLINE=1`)، فإقلاعها لا يعتمد على شبكةٍ خارجيّة. الأبطاء مرّةٌ واحدة.

### 8.2 أقلِع المكدّس

```bash
docker compose up -d
```

هذا وحده يكفي: الترتيب كلّه مُرمَّزٌ في `depends_on` وفحوص الصحّة — تقلع البيانات، ثمّ الأربع «لمرّةٍ واحدة» (‏شهادة TLS، تهيئة Vault، دلو MinIO، الهجرات والمنح)، ثمّ التطبيق والمُرحّل والحافّة.

راقب التقدّم:

```bash
docker compose ps
```

انتظر حتّى تصير الخدمات الطويلة `healthy` وتصير الأربع «لمرّةٍ واحدة» `Exited (0)`.

### 8.3 العمّال والمُرحّل

`outbox-relay` والعمّال الثلاثة يقلعون كلّهم تلقائيّاً مع `docker compose up -d` ([§3.133](log/3.133.md) ثمّ [§3.134](log/3.134.md)). **لا خدمة خلف `profile` بعد الآن**، فلا أمر إضافيّ. ما يستحقّ التنفيذ بعد الإقلاع هو **التحقّق** — لا تكتفِ بـ`Up`:

```bash
docker compose exec redis redis-cli XINFO CONSUMERS stream.media cg.media
```

مستهلكٌ واحدٌ مسجَّل بـ`pending 0` و`idle` بالثواني ⇒ حلقة `XREADGROUP` حيّة. عمليّةٌ عالقةٌ في جمودٍ تُبقي الحاوية `Up` إلى الأبد بينما `idle` يتضخّم بالساعات — و`docker ps` لا يفرّق بين الحالتين.

✅ **لا حاجة لإعادة تشغيل المُرحّل بعد ذلك.** مجموعات مستهلكي Redis ما تزال تُنشأ عند `$` (ذيل المجرى)، وهذا بالذات كان يجعل مجموعةً تُنشأ بعد نشرٍ على مجرًى جديد لا ترى تلك المدخلات أبداً — لكنّ `outbox-relay` نفسه صار يضمن الأزواج الأربعة كلّها قبل أوّل نشرٍ (`ensure_topology()`، [design/08-local-runbook.md §4](design/08-local-runbook.md)، `stream-topology-plan.md`)، بصرف النظر عن ترتيب إقلاعه مقابل خدمات `worker-*`.

> ✅ **العمّال الثلاثة موصولون بالكامل، ومقيسون كلّهم الآن.** `knowledge` موصولٌ منذ [§3.100](log/3.100.md) و`media` منذ [§3.104](log/3.104.md)، ولا واحد منهم ينهار لنقصِ محوّل. **وما أدخل كلّاً منهم المكدّسَ الافتراضيّ لم يكن ذلك الوصل بل قياسُ إقلاعه**: `memory` و`knowledge` بـ138 ثانيةً و≥ 5 دقائق (`RestartCount = 0` لكليهما — [§3.105](log/3.105.md))، ثمّ `media` بـ45 د 46 ث و`RestartCount = 0` ([§3.134](log/3.134.md)). القاعدة نفسها تبقى سارية على أيّ عاملٍ يُضاف لاحقاً: خدمةٌ غير مقيسةٍ بـ`restart: unless-stopped` في الإقلاع الافتراضيّ هي الطريقة التي يبدو بها مكدّسٌ سليمٌ معطوباً.
>
> ⚠️ `media` يحتاج زيادةً على ذلك **توجيه `image` في `PROVIDER_ROUTING`** و**اعتماداً مخزَّناً باسم `image:openai`**؛ نقصُ الأوّل يوقف الإقلاع برسالةٍ صريحة، ونقصُ الثاني يُفشل المهمّة بـ`credentials.*` لا العمليّة.

## 10) الأمان — قبل أيّ استخدامٍ حقيقيّ

### 10.1 ⚠️ Vault دائمٌ الآن — واقرأ هذا قبل أوّل اعتمادٍ حقيقيّ

**حُلّت مشكلة `-dev` (‏release-blockers-plan.md §3 خطوة 1)، وبقي قيدٌ آخر يجب أن تعرفه.** المكدّس لم يعد يشغّل `vault server -dev` (‏في الذاكرة بالكامل، تُمحى KV والTransit وAppRole عند كلّ إعادة تشغيل). بدلاً منه Vault يعمل بتخزين `file` دائم على حجمين مُسمَّيَين — `vault-data` (‏ما يملكه Vault نفسه) و`vault-init` (‏مفتاح فكّ الختم + التوكن الجذر، منفصلٌ عمداً) — و`deploy/vault/start.sh` هو ما يُقلع الحاوية الآن، ويقود Vault خلال `operator init`/`operator unseal` **قبل** أن يستطيع فحص الصحّة الإبلاغ بالنجاح.

**ما تغيّر عمليّاً:**

```bash
docker compose restart vault    # لا يمحو شيئاً بعد الآن
```

KV والTransit وAppRole **يبقَون**، ومفتاح Transit **نفسه لا يتجدّد** (‏مُثبَتٌ حيّاً — راجع `release-blockers-plan.md` §4). لا حاجة لإعادة تشغيل `vault-bootstrap` بعد إعادة تشغيل Vault.

**⚠️ لكنّ هذا وحده لا يكفي لإنتاجٍ حقيقيّ، وهذا مقصودٌ لا سهو.** لا يوجد KMS محلّيّاً يُفكّ الختم عبره تلقائيّاً بأمان، فمفتاح فكّ الختم والتوكن الجذر يُكتَبان في ملفٍّ نصّيٍّ عاديّ على حجم `vault-init` (`chmod 600`): `docker compose exec vault cat /vault/init/init.json`. أيّ من يصل ذلك الحجم — نسخةً احتياطيّةً لم تُشفَّر، أو جذر الخادم — يستطيع فكّ ختم Vault وقراءة **كلّ** سرٍّ يحرسه.

| استخدامك | ماذا تفعل |
|---|---|
| تجربة/عرض، لا اعتمادات مستخدمين حقيقيّة | اتركه كما هو — التخزين دائمٌ والمفتاح لا يتجدّد |
| **أيّ اعتمادٍ حقيقيّ لمستخدم** | ⛔ لا تكتفِ بهذا الإعداد. انسخ `vault-init` احتياطيّاً فوراً (أدناه)، ثمّ راجع مسار الترقية إلى KMS قبل تخزين أوّل بيانةٍ حقيقيّة |

**نسخٌ احتياطيّ واستعادة `vault-init`** (نفس الإجراء والتفصيل في `quickstart.md §5.2`):

```bash
docker compose exec vault cat /vault/init/init.json > vault-init-backup.json   # احفظه خارج المستودع، مُشفَّراً
# الاستعادة: انسخه إلى الحجم قبل إقلاع vault من جديد -- start.sh يفكّ الختم
# به بدل محاولة تهيئةٍ جديدة (يرفض ذلك تلقائيّاً إن وجد Vault مُهيَّأً بلا
# ملفٍّ محليٍّ يطابقه؛ راجع رسالة الخطأ في سجلّ الحاوية).
docker cp vault-init-backup.json aizzak-vault-1:/vault/init/init.json && docker compose restart vault
```

**مسار الترقية لإنتاجٍ حقيقيّ (وصفٌ لا تنفيذ):** auto-unseal عبر KMS خارجيّ (`seal "awskms"`/`"gcpckms"`/`"azurekeyvault"` في `deploy/vault/server.hcl`) يزيل الحاجة لتخزين مفتاح فكّ ختمٍ على القرص إطلاقاً؛ أو Transit auto-unseal عبر مثيل Vault **آخر** خارج هذا الخادم. كلاهما يحتاج تلك الخدمة موجودةً مسبقاً، فلم تُنفَّذ هنا. حوّل التطبيق نفسه إلى AppRole (`VAULT_TOKEN=` فارغ + `VAULT_ROLE_ID`/`VAULT_SECRET_ID` — راجع `quickstart.md §5` و08 §3.1) إن كنت لا تزال على وضع التوكن. هذا **القيد الأهمّ المتبقّي** في نشرٍ من خادمٍ واحد، ولا يمكن التحايل عليه.

### 10.2 المنافذ الداخليّة والجدار الناريّ — ⚠️ Docker يتخطّى `ufw`

هذه **أخطر نقطةٍ أمنيّةٍ خاصّةٍ بخادم Linux**، ولم تكن موجودةً على RunPod:

> **Docker يضيف قواعد `iptables` خاصّةً به تتخطّى `ufw`.** أيّ منفذٍ ينشره `docker-compose.yml` على المضيف (`ports:`) يصير مكشوفاً على كلّ واجهات الشبكة **حتّى لو منعه `ufw`**. وهذا يشمل `postgres:15432` و`redis:16379` و`qdrant:16333` و`vault:18200` و`minio` console‏ `:19001` — كلّها منشورةٌ افتراضيّاً (لحاجة جهاز التطوير)، وكلّها **لا يصحّ أن تلمس الإنترنت**.

عالج ذلك بواحدٍ من مسارين:

**المسار (أ) — جدارٌ ناريٌّ على مستوى الشبكة (الأبسط والموصى به):**
معظم المزوّدين (‏Hetzner Cloud Firewall، DigitalOcean، AWS Security Groups…) يقدّمون جداراً نارياً **قبل** الخادم، لا يتخطّاه Docker. من لوحة المزوّد **اسمح فقط** بـ`22`, `80`, `443`, و`19000` (‏إن لزم)، **وامنع كلّ ما عداها**.

**المسار (ب) — اربط المنافذ الداخليّة بـloopback (إن لم يكن ثمّة جدارٌ شبكيّ):**
على خادمٍ نظيفٍ لا داعي لنشر خدمات البيانات على المضيف أصلاً (‏كانت منشورةً لحزام اختبارات جهاز التطوير فقط). حرّر `docker-compose.yml` واسبق كلّ منفذٍ داخليٍّ بـ`127.0.0.1:`، مثلاً:

```yaml
    ports:
      - "127.0.0.1:${HOST_PORT_POSTGRES:-15432}:5432"   # postgres
```

طبّق الشيء نفسه على `pgbouncer` و`redis` و`qdrant` و`vault` وكونسول `minio` (`19001`). أبقِ `nginx` (`80`/`443`) وواجهة `minio` (`19000`) كما هي إن احتجت وصولاً خارجيّاً إليهما.

### 10.3 شهادة TLS — من ذاتيّة التوقيع إلى موثوقة

المكدّس يولّد شهادةً **ذاتيّة التوقيع** تلقائيّاً (`nginx-certs`)، فتعمل `https` لكنّ المتصفّح يحذّر. للحصول على شهادةٍ موثوقة:

- **الأبسط:** احصل على شهادةٍ لنطاقك (‏Let's Encrypt عبر `certbot`، أو من مزوّدك)، وضع ملفّيها في `deploy/nginx/certs/` باسمَي `server.crt` و`server.key` **قبل** أوّل `docker compose up -d`. سكربت `gen-cert.sh` **يترك أيّ شهادةٍ موجودةً كما هي** ولا يستبدلها — وهذا بالضبط كيف يزوّد نشرٌ حقيقيٌّ شهادته.
- عند التجديد: استبدل الملفّين ثمّ `docker compose restart nginx`.

**بعد أن يصير نطاقك ثابتاً (لا `localhost`)، فعّل HSTS بسطرٍ واحد** — لا تكتب ترويسةً يدويّاً ولا تُعدِّل بنية `nginx.conf`: أضف اسم نطاقك إلى الخريطة الموجودة فعلاً (P1‑7، `08-local-runbook.md §3.2‑ب`):

```nginx
    map $host $hsts_header {
        default "";
        "aizzak.example.com" "max-age=63072000; includeSubDomains";  # ← استبدل بنطاقك
    }
```

> ⚠️ **لماذا سطرٌ واحد لا تفعيلٌ عامّ:** المتصفّح يطبّق HSTS **لكلّ مضيف**، لا لكلّ تطبيقٍ أو منفذ. هذا `nginx.conf` نفسه — بلا تعديل — يخدم أيضاً `localhost` على أجهزة تطويرٍ أخرى؛ تفعيلٌ عامٌّ (`default "max-age=…"`) كان سيسمّم `localhost` لكلّ مشروعٍ آخر يعمل عليه أيّ مطوّر. اسمُ نطاقك تحديداً هو الآمن الوحيد. **لا تُفعِّله قبل أن تتأكّد أنّ الشهادة صالحة وأنّ HTTPS يعمل فعلاً** — HSTS يمنع المتصفّح من التراجع عن HTTPS لمدّة `max-age` بلا سبيل للتراجع اليدويّ إلّا مسح حالة المتصفّح.

### 10.4 السطح المكشوف — ملخّص

| المنفذ | التقييم |
|---|---|
| 80 / 443 (‏nginx) | مقصود. المصادقة عبر Firebase وحرّاس RBAC |
| 19000 (‏MinIO API) | إلزاميّ للروابط المُوقَّعة. الدلو خاصّ؛ الوصول بتوقيعٍ مؤقّتٍ فقط |
| 19001 (‏كونسول MinIO) | ⛔ **أغلقه في الإنتاج** — لوحةٌ إداريّةٌ بكلمة سرّ |
| 15432/16432/16379/16333/18200 | ⛔ **يجب حجبها** ([§10.2](#102-المنافذ-الداخليّة-والجدار-الناريّ--docker-يتخطّى-ufw)) |
| 22 (‏SSH) | فعّل المصادقة بمفتاحٍ فقط وعطّل كلمات السرّ |

## 11) التشغيل اليوميّ

### 11.1 أوامرٌ أساسيّة

```bash
docker compose ps                 # حالة كلّ خدمة
docker compose logs -f app        # سجلّ التطبيق حيّاً (Ctrl+C للخروج)
docker compose logs -f nginx      # سجلّ الحافّة
docker compose stop               # إيقافٌ مؤقّت (البيانات تبقى في الأحجام)
docker compose up -d              # تشغيل / استئناف
```

### 11.2 التحديث بعد تعديل الشيفرة

```bash
cd /opt/aizzak && git pull       # أو أعد rsync
docker compose build
docker compose up -d
```

الهجرات الجديدة تُشغَّل تلقائيّاً: تغيُّر الصورة يجعل `docker compose up -d` يعيد إنشاء `migrate` (‏وهو `app.ops.provision`) فيطبّق ما استجدّ ثمّ يخرج. ولفرضها صراحةً في أيّ وقت:

```bash
docker compose run --rm migrate
```

### 11.3 نسخٌ احتياطيّ

```bash
docker compose exec -T postgres pg_dump -U postgres -Fc aizzak > backup-$(date +%F).dump
```

للاستعادة إلى عنقودٍ نظيف: `docker compose exec -T postgres pg_restore -U postgres -d aizzak < backup-YYYY-MM-DD.dump`.

> 💡 لا تنسَ MinIO: بياناته في حجم `minio-data`. لنسخٍ كاملٍ خارج الخادم، استعمل `mc mirror` إلى تخزينٍ آخر، أو انسخ الحجم بـ`docker run --rm -v aizzak_minio-data:/data -v $PWD:/backup alpine tar czf /backup/minio.tgz -C /data .`.

### 11.4 إعادة تشغيل الخادم — الفخّ القديم زال، وبقي شيءٌ واحد يستحقّ الانتباه

**الفخّ الذي كان هنا (Vault في وضع dev يفقد كلّ شيءٍ عند إعادة التشغيل) زال مع release-blockers-plan.md §3 خطوة 1.** Vault يعمل الآن بتخزين `file` دائم ([§10.1](#101--vault-دائمٌ-الآن--واقرأ-هذا-قبل-أوّل-اعتمادٍ-حقيقيّ))، و`deploy/vault/start.sh` يفكّ الختم تلقائيّاً في كلّ إقلاعٍ للحاوية — سواءٌ عبر `docker compose up -d` أو عبر `restart: unless-stopped` بعد `reboot` للخادم نفسه. لا حاجة بعد الآن لإعادة تشغيل `vault-bootstrap` يدويّاً ولا للتفريق بين `up -d` و`docker start` من أجل Vault تحديداً.

```bash
cd /opt/aizzak && docker compose up -d      # ما زال المفضَّل: يتحقّق من كلّ الخدمات
```

**ما يستحقّ الانتباه الآن بدلاً من ذلك:** `vault-init` (‏مفتاح فكّ الختم + التوكن الجذر) حجمٌ Docker مثل أيّ حجمٍ آخر — إن حذفته أنت بالخطأ (`docker compose down -v`، أو `docker volume rm`) بينما `vault-data` بقي، فلا سبيل آليّاً لاستعادة الوصول. النسخ الاحتياطيّ مذكورٌ في §10.1.

## 12) جدول الأعطال

| العَرَض | الفحص والعلاج |
|---|---|
| `app` في حلقة إعادة تشغيل بـ`secret does not exist in Vault` | Vault دائمٌ الآن ([§10.1](#101--vault-دائمٌ-الآن--واقرأ-هذا-قبل-أوّل-اعتمادٍ-حقيقيّ)) فهذا لم يعد سببه فقدان الذاكرة عادةً — تحقّق من `docker compose ps vault-bootstrap` وسجلّه |
| `vault-start: ⛔ 'operator init' failed, and .../init.json does not exist` | حجم `vault-data` مُهيَّأٌ من قبل لكنّ `vault-init` مفقودٌ أو استُبدل — استعادة `init.json` من نسخةٍ احتياطيّة هي السبيل الوحيد ([§10.1](#101--vault-دائمٌ-الآن--واقرأ-هذا-قبل-أوّل-اعتمادٍ-حقيقيّ)) |
| التطبيق لا يقلع إطلاقاً | `FIREBASE_PROJECT_ID` فارغ ([§6.1](#61-القيم-التي-يجب-أن-تغيّرها)) — فشلٌ سريعٌ عند الإنشاء |
| نداءات LLM تفشل / لا ردّ من الوكيل | Ollama غير موصول. تحقّق: `docker compose exec app curl -s http://ollama:11434/api/tags` (‏خدمة) أو `http://host.docker.internal:11434/api/tags` (‏مضيف). راجع [§7](#7-الخطوة-5--ollama-على-لينكس-الفرق-الوحيد) و`PROVIDER_ROUTING` ([§6.2](#62-القيمة-التي-يجب-أن-تحوّلها-إلى-ollama)) |
| نداء LLM يفشل بـ404 | النموذج غير مسحوب: `docker compose exec ollama ollama pull gemma3:1b` (‏أو `ollama pull` على المضيف) |
| `provisioning failed` عند `migrate` | عادةً `AIZZAK_OWNER_PASSWORD` لا تطابق ما وُضع عند تهيئة العنقود — **حجمٌ قديمٌ بكلمة سرٍّ جديدة**. إمّا تعيد الكلمة القديمة، وإمّا تبدأ نظيفاً: `docker compose down -v` (‏⚠️ يمحو كلّ البيانات) ثمّ `up -d` |
| الحافّة 502/504 بينما `ps` يقول `healthy` | راجع حالة خدمة **`nginx` نفسها** ([§9.1](#91-فحوص-الحياة-والجاهزيّة)) |
| `https://<خادمك>` يرفض الاتّصال | لم تُولَّد الشهادة أو مُنِع 443: `docker compose up -d nginx-certs` ثمّ `restart nginx`، وافتح 443 في الجدار الناريّ |
| رابط MinIO مُوقَّعٌ لا يفتح في المتصفّح | `MINIO_PUBLIC_ENDPOINT` لا يطابق عنواناً يصله المتصفّح، أو 19000 محجوب ([§6.3](#63-القيم-التي-تضبطها-حسب-طريقة-ollama-والعنوان-العامّ)). لا يُصلَح بعد التوقيع |
| `POST /search` يعيد 503 | خدمة `embedding` غير صحيحة: `docker compose ps embedding` وسجلّها. النموذج يحتاج ≈ 30 ثانيةً بعد الإقلاع |
| أحد `worker-*` ينهار عند الإقلاع | **عطلُ بيئةٍ لا نقصُ كود، أيّاً كانت الخدمة** ([§8.3](#83-العمّال-والمُرحّل)): Vault · سرّ MinIO · `PROVIDER_ROUTING` (‏و`media` يضيف: مدخلةَ `image` واعتمادَ `image:openai`) — اقرأ الرسالة، فهي تسمّيه |
| الأحداث لا تصل العامل | حالة `outbox-relay`؛ `published_at` في `platform.outbox`؛ **ووجود مجموعة المستهلك وتأخّرها** (`docker compose exec redis redis-cli XINFO GROUPS stream.<وحدة>`). **ترتيب الإقلاع لم يعد سبباً محتملاً** ([§8.3](#83-العمّال-والمُرحّل)) |
| نموّ ذاكرة Redis | `docker compose exec redis redis-cli XLEN stream.<وحدة>` — المجاري إلحاقيّة و`XACK` **لا يحذف**. `STREAM_MAXLEN` سقفٌ لا حلّ؛ راقب `XLEN` |
| صفر صفوفٍ رغم وجود بيانات | لم يُضبط `app.workspace_id` (‏RLS) — تحقّق من `ExecutionContext`/`rls.py` |
| رفض اتّصال Postgres من التطبيق | يجب أن يمرّ عبر PgBouncer (`pgbouncer:6432`) لا `postgres:5432`؛ راجع حجم التجمّع |
| Vault يعمل ساعةً ثمّ يفشل كلّ سرّ | انتهاء `token_ttl=1h` (توكن AppRole للتطبيق). العلاج منفَّذٌ في الشيفرة (إعادة مصادقةٍ واحدة عند 401/403) — تحقّق أنّ `relogin` موصول |
| منفذٌ داخليٌّ مكشوفٌ للإنترنت | Docker يتخطّى `ufw` ([§10.2](#102-المنافذ-الداخليّة-والجدار-الناريّ--docker-يتخطّى-ufw)) — استعمل جدار المزوّد أو اربط بـ`127.0.0.1` |
| بعد `reboot` لا يعمل شيء | `sudo systemctl enable --now docker` ([§3.3](#33-شغّل-docker-مع-كلّ-إقلاعٍ-للنظام)) ثمّ `docker compose up -d` |

**أوامرٌ تشخيصيّةٌ سريعة:**

```bash
docker compose logs --tail=200 app
```

```bash
docker compose restart app
```

```bash
docker compose exec app env | sort   # تحقّق من المتغيّرات الفعليّة داخل الحاوية
```

## 13) القواعد الذهبيّة لهذا النشر

1. **خادم Linux يدعم `docker compose` كاملاً** — لا صورةَ خاصّة ولا إعادة هيكلة؛ المسار الأقرب إلى التصميم.
2. **الانحراف الوحيد هو Ollama**: اربطه خدمةً في compose (الأبسط) أو على المضيف مع `host.docker.internal` ([§7](#7-الخطوة-5--ollama-على-لينكس-الفرق-الوحيد)).
3. **حوّل `PROVIDER_ROUTING` إلى Ollama** — قيمة `.env.example` الافتراضيّة سحابيّةٌ محجوبة.
4. **`MINIO_PUBLIC_ENDPOINT` يجب أن يطابق عنواناً يصله المتصفّح فعلاً** — لا يُصلَح بعد التوقيع.
5. **Docker يتخطّى `ufw`** — احجب المنافذ الداخليّة بجدار المزوّد أو بربط `127.0.0.1` ([§10.2](#102-المنافذ-الداخليّة-والجدار-الناريّ--docker-يتخطّى-ufw)).
6. **`docker compose up -d` بعد أيّ إعادة تشغيل** — يبقى المفضَّل عموماً، لكن Vault تحديداً لم يعد يفقد شيئاً بأيّ طريقةٍ ([§10.1](#101--vault-دائمٌ-الآن--واقرأ-هذا-قبل-أوّل-اعتمادٍ-حقيقيّ)).
7. **العمّال الثلاثة يقلعون مع `up -d`** ولا `profile` في الملفّ — و`WORKER` لم يعد يعني شيئاً لـCompose. تحقّق بـ`XINFO CONSUMERS` لا بـ`docker ps`.
8. **Vault دائمٌ الآن، لكنّ `vault-init` (المفتاح + التوكن) عاديٌّ غير مُشفَّر على القرص** — انسخه احتياطيّاً قبل أيّ اعتمادٍ حقيقيّ، وراجع مسار الترقية إلى KMS قبل إنتاجٍ فعليّ.
9. **`FIREBASE_PROJECT_ID` الفارغ = تطبيقٌ لا يقلع**، لا مجرّد مصادقةٍ معطّلة.
10. **حاويةٌ `healthy` ليست دليلاً على مسار بيانات** — الدليل في `deploy/smoke/`.
11. **`.env` لا يُنقل ولا يُرفع** — أنشئه على الخادم، وأبقِه خارج git.
